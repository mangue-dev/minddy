Every project can have a nested wiki of pages. Pages are for durable context: specifications, decisions, conventions, runbooks, onboarding, and the reasoning a ticket depends on. Issues remain the right place for work to be done. Pages support markdown, subpages, attachments, threaded comments, backlinks from pages that link to them, read-only sharing, export, and history. Favorite pages surface for the whole project at the top of the page tree, and avatars show who is viewing a page live. A page opened from a mention, a backlink, a page resource of an issue or objective, or a page link in a comment or a Numo answer opens in a side panel over the current screen; **Expand** opens the full page. Database pages always open as full pages. Hovering a mention, a backlink, a page resource, a relation, an issue's objective or a person in activity shows a card without leaving the screen: an issue's full card, an objective's status, progress, issues and relations, the first lines of a page, routine, skill or the task notebook, a database's first rows, a person's email and project role, a pull request's state and branches, an MCP server's sign-in state and tool count, a cycle's progress, a project's members and their roles. Clicking the card opens what the mention opens. A target the reader cannot open shows nothing more.

Several people can edit the same page at the same time, including the same paragraph and the title: changes merge character by character and appear for the others as they are typed, with each editor's caret shown in their color and labeled with their name. A page saves as it is typed; unsaved changes survive a dropped connection and moving to another page while minddy stays open, and the browser warns before closing with unsaved changes. A change the server refuses is undone with a message.

Page content supports headings, lists, tasks, code, collapsible sections, and colored callouts with editable emoji icons. Callouts keep their icon and palette color in Markdown exports and when agents read or write a page. Published pages can also be shown as tabs beside the project's public feedback board.

Numo and MCP-connected agents can search, read, write, and attach pages to issues or objectives. Their page edits appear live for anyone who has the page open. Appending a block or rewriting a passage applies to the page as it is at that moment, keeps text others typed meanwhile, and leaves the blocks it does not change exactly as they were. When answering a question about project-specific decisions, Numo should search and read the relevant pages instead of guessing. A linked page is a live resource: its title continues to update if the page is renamed.

Owners and Members can turn a page into an issue with **Promote to issue**, in the page tree menu, the open page's `…` menu, or the handle menu of a single database entry (there is no bulk promotion from a multi-row selection). Readers do not see the action. Unsaved changes on the open page are saved first; if that save fails, minddy reports it and Numo does not open. Numo then reads the page (title, content and, for a database entry, its properties), asks questions when the page is unclear or a database leaves the issue's scope ambiguous, creates one issue and attaches the page to it. Unlike a promoted notebook task, the page stays where it is.

## Page databases

Use the **+** menu in Pages to create a page or a database. A new database has only its entry name, with no optional columns. Its dismissible **New database** banner offers **Create with Numo**, which opens Numo and asks it to help define the database by asking questions, and **Import an existing database**. Add Text, Number, Select, Multi-select, Created at, Date, People, or Checkbox columns using **Add column** in **Columns** or the **+** column at the right edge of the table. A database holds up to 30 property columns in addition to its entry name, 100 options per Select or Multi-select column, and 2,000 characters per text cell. The creation dialog has a searchable column-type picker. Numbers accept signed decimals (with a dot or comma) and reject letters. Created at shows the entry’s original creation timestamp and cannot be edited.

Select allows one option; Multi-select allows several. Search existing options or create a new one directly in the cell menu. Choose **Edit options** there or in Columns to open the options dialog. Edit names in fixed-size fields, choose colors with compact swatches, move options with the up/down buttons, or remove an option with its trash button. Save applies all draft changes together; Cancel discards them. Saved deletions remove the option from live and trashed entries, clearing a single selection or retaining the remaining multiple selections. New options created in a cell or dialog receive a random unused palette color within the column; colors can repeat once the ten-color palette is exhausted. Single-select badges are pills; multi-select badges have square corners. Both use tinted backgrounds and matching text without color dots.

Use the eye beside a column to show or hide it. Click a column header to rename it, or choose **Edit column** to change the type of a custom column. The edit dialog converts existing values when you save a new type. If some values cannot be converted, a warning tells you how many cells will be cleared. Continue to convert compatible values and clear only incompatible cells, or cancel to keep the column and all its values. Changing to Created at uses each entry’s original creation date and warns before replacing existing values.

The header highlights on hover and keeps the default cursor. Move the pointer while holding a header to reorder columns horizontally; the Name column always stays first. The cursor changes when dragging starts. Enter or Space on a focused header opens its actions. F8 starts keyboard reordering; Left/Right moves, Enter confirms, and Escape cancels. You can also reorder or delete columns in the Columns menu. Deleting a column removes its values from every entry and cannot be undone.

Each database entry is a full page. An empty entry body shows a writing placeholder. Open an entry from the list to edit it in a floating panel, then choose **Extend** to open it as a full page. Extend waits for pending document saves and keeps the panel open if saving fails. An empty entry remains in the database until you delete it.

Empty table cells stay blank. Edit values by clicking anywhere in their list cell or above an entry's page content. List rows are 40 px tall and clip long values; text previews are shortened without changing the saved text. The table, floating entry panel, and extended entry page share the same text and number editor. It overlays the value, expands without moving other rows, and remains inside the visible viewport. Enter saves, Escape cancels, and Shift+Enter adds a line to text. Leaving the editor saves; an invalid number keeps the editor open until fixed, and a failed save reverts the value with an error. One person appears with an avatar and name, while multiple people appear as overlapping avatars. People selects one or more project members and notifies newly mentioned members. A database shows its entries through named views listed above the table, like the issue board. Each view keeps its own sort, filter and hidden columns, and every project member sees the same views. The owner or a Member adds a view with **New view** (+), starting from the view on screen, renames or deletes the active view from its options menu (⋯), and drags views to reorder them for everyone; sort, filter and column changes are saved to the active view. A database keeps at least one view and shows the default **Table** view until its first change. Readers switch views and can adjust one for themselves until they leave the page. The browser remembers the view each person last opened; search is never saved. Manual ordering is shared with the page tree. The table reaches the right edge while the page title and controls keep their margins. All data columns scroll horizontally. Only the row-selection checkbox stays overlaid at the left edge; its opaque background covers the full row height flush with the left edge when pinned. It appears on direct checkbox or row hover or while selected, and remains accessible by keyboard. Horizontal scrolling works from anywhere on the page: the title, header, sidebars, controls, margins, and empty areas. Use a horizontal trackpad gesture, Shift + mouse wheel, or a horizontal touch swipe. Vertical gestures keep scrolling the page normally, and pinch zoom remains available. The synchronized scrollbar at the bottom of the screen also supports the keyboard without covering table rows.

Hover over an entry to reveal its gutter. Moving anywhere over the selection container reveals its checkbox, including after horizontal scrolling. Clicking anywhere in that container toggles row selection, including its edges and corners. The handle opens entry actions and can drag entries in manual order. Select several entries with their checkboxes, or Shift-click to select a range, then confirm duplication or moving the selection to the recoverable trash. The gutter **+** inserts below that entry; hold **Option/Alt** to insert above. Adjacent insertion clears the active view's filter so the new entry is visible.

Database entries support the usual rich text editor, comments, attachments, duplication, and trash restoration. Entries with stored column values remain visible in the trash even without a title or body. If an entry was deleted separately from its database, restore the database first, then the entry. Entries with stored values can be reordered within their database, but cannot be moved outside it.

PDF exports include database entries and their column values. **Export → Database archive (.zip)** includes the complete branch: readable Markdown and CSV, exact column schemas and option colors, values, entry bodies, creation timestamps, nested pages, and attached file bytes. Import this archive through a new database’s banner to restore it, including remapped internal page/file links. People can be matched to members of the destination project. Saved database views are not part of the archive; duplicating a database keeps them. Published database pages only show entries included in the published branch; publishing a database without its children keeps their content private. Numo and MCP-connected agents read database schemas, option definitions, entry values, and creation timestamps through page tools. They can create databases and entry pages, rename or reorder columns, manage selection options, and update values using the same access checks and conflict protection as the interface. MCP exposes these operations through `minddy_create_page` (`database: true`), `minddy_get_page`, and `minddy_update_page_database`; Numo uses `create_page`, `get_page` in the conversation, or `read_page` during delegated repository work, plus `update_page_database`. Agents can create an entry with all its values in one call (`values` on page creation) and change several values of one entry at once (`operation=values`), which writes every cell together or none. Schema edits require the current database revision; cell edits require the exact previous value of each cell. Column type changes use a preview followed by an apply with its token. Clearing incompatible values requires explicit confirmation, and concurrent changes invalidate the preview. MCP writes retain the connected agent’s identity.

Advanced formulas are not part of page databases. Numo and MCP do not read or change database views.

Date properties support an optional time. Choose a day, enable **Add a time**, and enter **Time** without closing the picker. Dates without a time remain calendar strings (`YYYY-MM-DD`); timed values are ISO timestamps displayed in the device’s time zone, including an explicitly chosen midnight. Turning off the time keeps the displayed calendar day. Date filters match that displayed day, and sorting treats untimed dates as local midnight. The same validation applies to UI, agent and MCP saves, database import and text-to-date conversion.

## Import a database

From a new database’s banner, choose **Import an existing database**. Upload a Notion **Markdown & CSV** ZIP with subpages included, a database CSV, or a Minddy database archive. If the archive contains several databases, choose one. Review the suggested column names and types, then review the page count and confirm. Numo can suggest types from a small sample when import assistance is available; manual mapping remains available. Unsupported source properties remain text, and incompatible values block the import instead of being silently cleared. Notion exports do not include their original schema, option colors, or formula definitions, so only information present in the export can be imported.

The import includes entry bodies, nested documents, and local files. It requires a database with no optional columns or existing entries. A failed database write rolls back all imported rows; retrying the same import does not create duplicates. Archives are limited to 20 MB compressed, 50 MB expanded, and 1,000 pages. Each attachment retains the existing 10 MB page-file limit.

The option editor offers **Add an option** below its rows, including for empty Select and Multi-select columns. Give options distinct, nonempty names before saving. The new-database setup area offers Numo and import cards; its dismiss control has a tooltip.

The project owner can create a database-arrival routine with typed property filters. An empty entry stays armed until edited to satisfy its conditions. Removing a referenced property or changing its type suspends the filter with a readable error. Creation, duplication, database import and allowed moves are arrivals; restoration is not. Configure these in Routines, not the database schema editor.
