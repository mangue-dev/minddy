Project owners manage project settings, members, categories, recurrences, the linked Git repository, import, integrations, and feedback boards. Account settings belong only to the current user and include identity, interface language, personal preferences, notifications, AI providers, the default Numo model and Numo's memory. From their profile, users pick a generated avatar or upload their own image, and the avatar follows them across projects, comments, and conversations. A project member can work on issues and categories according to the available product permissions, but cannot change owner-only settings.

Numo can change most of these settings on request. Project-side, `update_project` covers name, key and accent color, Smart Assign and its per-member rules, Smart Triage's static rules engine, the feedback AI review and translation options. Account-side, `update_account_settings` covers the display name, interface language, display theme, the light-mode and dark-mode palettes (`theme_light`, `theme_dark`, each limited to its own mode, `null` resetting it to Minddy) and popover transparency (`theme_transparency`), the keyboard send shortcut, the first day of the week (`week_start`: `auto` follows the interface language, or Monday, Sunday or Saturday; it orders date pickers, routine days and the activity grid), whether voice dictations are cleaned up before insertion (`dictation_cleanup`; off inserts the raw transcription), where Numo-created issues land, auto-assign and Smart Fill preferences (including whether Smart Fill links related issues, `smart_fill_relations`, whether it re-evaluates edited issues, `smart_fill_reevaluate`, and whether it writes the title of an issue created without one, `smart_fill_title`, on by default), whether the user's issues are indexed as private vectors (`issue_indexing`), the personal cycle knobs, the Inbox notification toggles, whether copying an issue's prompt starts it, whether Numo keeps a memory of the user (`numo_memory`; off, Numo neither reads nor saves memories and the saved ones are kept), whether Numo works in the background (`numo_background`, on by default; it needs `numo_memory` on), and analytics consent. Project automations and account presets are retired: they no longer run, and they are not converted into routines. To schedule or trigger Numo work, the owner creates a routine in Routines. Pending and human-waiting old chains stop. Account settings → AI holds the Minddy AI providers used by Numo, routines, automations, voice and feedback. Several API providers can remain connected; capability routing selects one compatible provider per family, and usage switches determine which features use its key. The default Numo model is saved per user and provider: App default or a specific available model. An explicit conversation model overrides it; a conversation following the default picks up later changes, while an admitted turn keeps its frozen model. Settings that Numo can explain but never change: the dictation vocabulary (Account settings → Preferences → Vocabulary: spellings, and replacements for what dictation hears instead), the personal Numo model default (Account settings → AI only) and the credentials themselves: AI provider keys, GitHub or GitLab connections, two-factor authentication, and the avatar file, which stay user-driven.

minddy does not sell data or use it for advertising. The Data section of account settings lets users download a JSON transfer file and restore it on another minddy instance. The transfer is additive and preserves project, issue, page, and personal-data IDs whenever the destination can safely reuse them; conflicts receive new IDs and are reported after import. Project memberships are restored only when the referenced project already exists on the destination. Personal Numo model preferences are included and rebound to the importing account, without provider credentials. Passwords, API keys, OAuth tokens, repository credentials, and billing subscriptions are never transferred. Repository access tokens are encrypted before storage and are used only when a user triggers an action that needs the connected repository.

Numo's memory holds short notes Numo keeps about the user: preferences, facts about their work and standing instructions, each for all projects or for one. Numo saves one with `remember` when the user asks it to remember something or states a lasting preference, rewrites one by passing its id in `replaces`, and deletes one with `forget`. A user keeps at most 100 memories of 1,000 characters each. Memories are private to their user and are read in every conversation, routine and `@Numo` mention, but only a conversation can change them. Account settings → AI & Numo → Numo's memory lists them, edits or deletes each one, offers Forget everything, and holds the switch that turns memory off.

Numo's journal holds one-sentence entries Numo writes for the user: what waits for them (a review they owe, an answer they expect) and, in a routine or an `@Numo` mention, what Numo changed in their content. Numo adds one with `journal_write` (with the project it concerns, or none) and closes one with `journal_close` and a reason once it no longer applies; its open entries are listed in its prompt. In an `@Numo` mention or a routine, Numo sees and closes only the entries about that project and those about no project. Entries have no type, only a lifecycle: written, seen by the user, closed. They are private to their user, send no notification, are capped at 50 open entries, closed ones are deleted within 180 days, and entries left open are deleted after 180 days. Account data export includes them. The user cannot browse the journal entry by entry; Home sums it up instead (see below).

Numo in the background (Account settings → AI & Numo → Numo in the background, `numo_background`, on by default and only active while Numo's memory is on) wakes Numo a few minutes after workspace events that concern the user or that a memory asks it to watch for. Each wake is one ordinary Numo turn, with the user's tools and model, in a conversation of its own that the conversation list leaves out and that is deleted after 30 days; it reports in the journal, which Home sums up and which the user can also read by asking Numo in a conversation. The server guards every call of that turn. In a project with other members (or a pending invitation), Numo changes only what is the user's: issues assigned to them or that they created, objectives they lead, pages they created, the feedback of a board they own; creating content there or changing anything else needs `authorized_by`, the id of a memory of the user that allows it and applies to that project. In every project, trashing or restoring, removing members or integrations, pull request actions, external MCP calls, project administration, account settings and public feedback replies need such a memory too. A note needs that memory, or `urgent: true` with a reason, capped at two urgent notes in 24 hours. Screening events and each wake count toward the user's AI usage. An administrator caps wakes per member in 24 hours (Background turns per day in the Assistant card of Models, 20 by default, 0 switches it off). Turning the switch off cancels a wake that has not started. To allow an action Numo asked about in the journal, the user tells Numo in a conversation and Numo saves the memory.

Home is a Numo conversation (MIN-930): the same view as the Numo panel without its header, sharing its conversation. Each time Home is shown it opens a new conversation, unless a reply is still running; the previous one stays in the history, and the conversation started on Home continues in the panel. The New conversation button at the top right starts another. Home shows no account notices while it is a conversation; on an instance without AI it shows the greeting and the notices (pending invitations, Smart Assign warning, desktop and mobile install prompts). The Home summary (admin setting Home summary model, `home_brief_model`): under the greeting of the new conversation, a few sentences from Numo that sum up the journal's open entries and the closed ones the user has not seen, what waits for them first, then what Numo did that touches their content, then what it offers to do on its own, with typed mentions. It is rewritten in the background by one short call after each Numo turn that writes or closes a journal entry, never when Home opens; each rewrite is a new version, the last 50 are kept, and the account data export includes them. Home shows it only while the entries it covers are in the state it was written for (an entry closed or deleted since hides it until the next rewrite, which Home's read schedules), and not once all of them are settled and seen. Showing it marks the covered entries seen. "See what Numo did" loads the conversation of the newest covered entry in Home. The summary is not saved in the conversation and Numo does not read it when it answers; it stays on top of the conversation started under it on Home. The same call writes zero to four suggestions that replace Home's fixed suggestion rows and double as quick answers such as "Yes, do it on your own from now on". Background Numo off: no summary, fixed rows. It counts toward the user's AI usage. Home no longer lists "X has 2 issues in triage" rows; Numo is instructed to note waiting triage in the journal when it sees it in a project the user owns, which is best effort, not a guaranteed signal.

Numo's reminders (Account settings → AI & Numo → Reminders) are one-off "when X, do Y" requests Numo records with `create_watch`, only in a conversation the user holds with Numo: routines, `@Numo` mentions and background wakes can't set or cancel them, and routines and mentions don't see them. A reminder is a condition on one issue (it reaches a status, `done` by default, or someone other than the user comments on it, a forge or integration comment included), one objective (it reaches a status) or a date within 90 days, given with its offset, plus an instruction of 500 characters at most and an action. With `notify`, the user gets a Numo message in Inbox with the instruction; with `act`, the message says Numo is on it and a Numo turn carries the instruction out in the conversation the reminder came from (a new conversation, titled with what happened, when that one is gone or busy), with the user's tools and rights at that moment and the user's time zone. That turn runs unattended: it doesn't ask questions, write memories, set reminders or take a sensitive action (trash, pull request, external MCP, member or integration removal, account settings, public feedback reply). Without AI usage left, or when the turn fails, the user gets a message saying Numo did not act. Nothing runs and no AI usage is counted until the condition holds: the routines clock reads the current state every five minutes. A reminder fires once, expires after 90 days (a date reminder a day after its date), and a user keeps at most 20 active ones; one on a status the record already has is refused. A reminder waits while its record is in the trash and is cancelled when the record is deleted for good or the user loses access to its project. Numo lists them with `list_watches`, replaces one through `replaces` and cancels one with `cancel_watch`; the user cancels them in settings. A reminder is not a routine: it fires once for one record, while a routine runs on every schedule or event. Instructions are private to their user, fired, cancelled and expired reminders are deleted after 90 days, and account data export includes them. An `act` reminder turn that changed the user's content writes one journal entry about it, so the Home summary reports that work (MIN-930); a `notify` reminder is only an Inbox note and never reaches the summary.
