Project owners manage project settings, members, categories, recurrences, the linked Git repository, import, integrations, and feedback boards. Account settings belong only to the current user and include identity, interface language, personal preferences, notifications, AI providers, the default Numo model (personal keys only) and Numo's memory. From their profile, users pick a generated avatar or upload their own image, and the avatar follows them across projects, comments, and conversations. A project member can work on issues and categories according to the available product permissions, but cannot change owner-only settings.

Numo can change most of these settings on request. Project-side, `update_project` covers name, key and accent color, Smart Assign and its per-member rules, Smart Triage's static rules engine, the feedback AI review and translation options; the owner also invites members as member or reader (`invite_member` with `role` and `can_comment`) and changes a member's or a pending invitation's role (`update_member_role`; demoting a member to reader unassigns their open issues and objective leads). Account-side, `update_account_settings` covers the display name, interface language, display theme, the light-mode and dark-mode palettes (`theme_light`, `theme_dark`, each limited to its own mode, `null` resetting it to Minddy) and popover transparency (`theme_transparency`), the keyboard send shortcut, the first day of the week (`week_start`: `auto` follows the interface language, or Monday, Sunday or Saturday; it orders date pickers, routine days and the activity grid), whether voice dictations are cleaned up before insertion (`dictation_cleanup`; off inserts the raw transcription), the dictation vocabulary (`dictation_vocabulary`: spellings, and replacements for what dictation hears instead; the list is replaced whole), the coding agent preferences (`prompt_send_to_agent` opens prompts in the agent's app instead of copying them, `prompt_send_agent` picks Claude, Codex or Cursor), where Numo-created issues land, auto-assign and Smart Fill preferences (including whether Smart Fill links related issues, `smart_fill_relations`, whether it re-evaluates edited issues, `smart_fill_reevaluate`, whether it writes the title of an issue created without one, `smart_fill_title`, on by default, and whether it completes new objectives, `smart_fill_objectives`, and names an objective created without a name, `smart_fill_objective_name`), whether the user's issues are indexed as private vectors (`issue_indexing`), the personal cycle knobs, the Inbox notification toggles, whether copying an issue's prompt starts it, whether Numo keeps a memory of the user (`numo_memory`; off, Numo neither reads nor saves memories and the saved ones are kept), whether Numo works in the background (`numo_background`, on by default; it needs `numo_memory` on), analytics consent, and which projects the user hid from their navigation (`hide_project_ids`, `show_project_ids`; hiding is personal). Project automations and account presets are retired: they no longer run, and they are not converted into routines. To schedule or trigger Numo work, the owner creates a routine in Routines. Pending and human-waiting old chains stop. Account settings has a Numo tab (the memory and background switches, where Numo-created issues land, memories and reminders), an AI tab that holds the Minddy AI providers and Numo's model choice (personal keys only) used by Numo, routines, automations, voice and feedback, and an MCP tab with both directions: assistants connected to minddy, then the MCP servers Numo connects to. Several API providers can remain connected; capability routing selects one compatible provider per family, and usage switches determine which features use its key. On minddy Cloud, Numo's model and reasoning level come from the instance's configuration and cannot be chosen. With a personal key, the default Numo model is saved per user and provider: App default or a specific available model. An explicit conversation model overrides it; a conversation following the default picks up later changes, while an admitted turn keeps its frozen model. Settings that Numo can explain but never change: the providers and models of each AI usage, including the personal Numo model default (Account settings → AI only), and the credentials and identities themselves: AI provider keys, GitHub or GitLab connections, sign-in, two-factor authentication and sessions, the apps authorized to connect to minddy, the avatar and project icon files, ownership transfers, account export and deletion, which stay user-driven.

minddy does not sell data or use it for advertising. The Data section of account settings lets users download a JSON transfer file and restore it on another minddy instance. The transfer is additive and preserves project, issue, page, and personal-data IDs whenever the destination can safely reuse them; conflicts receive new IDs and are reported after import. Project memberships are restored only when the referenced project already exists on the destination. Personal Numo model preferences are included and rebound to the importing account, without provider credentials. Passwords, API keys, OAuth tokens, repository credentials, and billing subscriptions are never transferred. Repository access tokens are encrypted before storage and are used only when a user triggers an action that needs the connected repository.

Numo's memory holds short notes Numo keeps about the user: preferences, facts about their work and standing instructions, each for all projects or for one. Numo saves one with `remember` when the user asks it to remember something or states a lasting preference, rewrites one by passing its id in `replaces`, and deletes one with `forget`. A user keeps at most 100 memories of 1,000 characters each. Memories are private to their user and are read in every conversation, routine and `@Numo` mention, but only a conversation can change them. Account settings → Numo → Memories lists them, edits or deletes each one and offers Forget everything; the Numo card above it holds the switch that turns memory off.

Numo's journal holds one-sentence entries Numo writes for the user: what waits for them (a review they owe, an answer they expect) and, in a routine or an `@Numo` mention, what Numo changed in their content. Numo adds one with `journal_write` (with the project it concerns, or none) and closes one with `journal_close` and a reason once it no longer applies; its open entries are listed in its prompt. In an `@Numo` mention or a routine, Numo sees and closes only the entries about that project and those about no project. Entries have no type, only a lifecycle: written, seen by the user, closed. They are private to their user, send no notification, are capped at 50 open entries, closed ones are deleted within 180 days, and entries left open are deleted after 180 days. Account data export includes them. The user cannot browse the journal entry by entry; Home sums it up instead (see below).

Numo in the background (Account settings → Numo → Numo in the background, `numo_background`, on by default and only active while Numo's memory is on) wakes Numo a few minutes after workspace events that concern the user or that a memory asks it to watch for. Each wake is one ordinary Numo turn, with the user's tools and model, in a conversation of its own that the conversation list leaves out and that is deleted after 30 days; it reports in the journal, which Home sums up and which the user can also read by asking Numo in a conversation. The server guards every call of that turn. In a project with other members (or a pending invitation), Numo changes only what is the user's: issues assigned to them or that they created, objectives they lead, pages they created, the feedback of a board they own; creating content there or changing anything else needs `authorized_by`, the id of a memory of the user that allows it and applies to that project. In every project, trashing or restoring, removing members or integrations, pull request actions, external MCP calls, project administration, account settings and public feedback replies need such a memory too. A note needs that memory, or `urgent: true` with a reason, capped at two urgent notes in 24 hours. Screening events and each wake count toward the user's AI usage. An administrator caps wakes per member in 24 hours (Background turns per day in the Assistant card of Models, 20 by default, 0 switches it off). Turning the switch off cancels a wake that has not started. To allow an action Numo asked about in the journal, the user tells Numo in a conversation and Numo saves the memory.

Home is a Numo conversation (MIN-930): the same view as the Numo panel without its header, sharing its conversation. Each time Home is shown it opens a new conversation, unless a reply is still running; the previous one stays in the history, and the conversation started on Home continues in the panel. The New conversation button at the top right starts another. Home shows no account notices while it is a conversation; on an instance without AI it shows the greeting and the notices (pending invitations, Smart Assign warning, desktop and mobile install prompts). The Home summary (admin setting Home summary model, `home_brief_model`): under the greeting of the new conversation, a few sentences from Numo that sum up the journal's open entries and the closed ones the user has not seen, what waits for them first, then what Numo did that touches their content, then what it offers to do on its own, with typed mentions. It is rewritten in the background by one short call after each Numo turn that writes or closes a journal entry, never when Home opens; each rewrite is a new version, the last 50 are kept, and the account data export includes them. Home shows it only while the entries it covers are in the state it was written for (an entry closed or deleted since hides it until the next rewrite, which Home's read schedules), and not once all of them are settled and seen. Showing it marks the covered entries seen. The summary carries what the user needs to know, including the key facts and figures of a result Numo produced (a project summary, research), with no link to another conversation; journal entries about such results carry those facts. The first message sent under the summary carries its id, and the server stores the summary as Numo's first message of the new conversation (MIN-933): Numo reads it as its own previous message, and the panel and history show it; once the user writes, the greeting goes and the summary stays on top of the conversation started under it on Home, as Numo's opening message; with no summary nothing stays. The same call writes zero to four suggestions that replace Home's fixed suggestion rows and double as quick answers such as "Yes, do it on your own from now on". Background Numo off: no summary, fixed rows. It counts toward the user's AI usage. Home no longer lists "X has 2 issues in triage" rows; Numo is instructed to note waiting triage in the journal when it sees it in a project the user owns, which is best effort, not a guaranteed signal.

Numo's reminders (Account settings → Numo → Reminders) are "when X, do Y" requests Numo records with `create_watch`, one-off or recurring, only in a conversation the user holds with Numo: routines, `@Numo` mentions, background wakes and a reminder's own turn can't set, change or cancel them, and routines and mentions don't see them. A reminder is a condition on one issue (it reaches a status, `done` by default, or someone other than the user comments on it, a forge or integration comment included), one objective (it reaches a status) or a date within 90 days, given with its offset, plus an instruction of 500 characters at most and an action. With `notify`, the user gets a Numo message in Inbox with the instruction; with `act`, the message says Numo is on it and a Numo turn carries the instruction out in the conversation the reminder came from (a new conversation, titled with what happened, when that one is gone or busy), with the user's tools and rights at that moment and the user's time zone. That turn runs unattended: it doesn't ask questions, write memories, set reminders or take a sensitive action (trash, pull request, external MCP, member or integration removal, account settings, public feedback reply). Without AI usage left, or when the turn fails, the user gets a message saying Numo did not act. Nothing runs and no AI usage is counted until the condition holds: the routines clock reads the current state every five minutes. A reminder fires once, expires after 90 days (a date reminder a day after its date), and a user keeps at most 20 active ones; one on a status the record already has is refused. A reminder waits while its record is in the trash and is cancelled when the record is deleted for good or the user loses access to its project. Numo lists them with `list_watches`, replaces one through `replaces` and cancels one with `cancel_watch`; the user cancels them in settings. A one-off reminder fires once for one record. Instructions are private to their user, fired, cancelled and expired reminders are deleted after 90 days (a paused one stays), and account data export includes them. An `act` reminder turn that changed the user's content writes one journal entry about it, so the Home summary reports that work (MIN-930); a `notify` reminder is only an Inbox note and never reaches the summary.

Recurring reminders (MIN-953) are the personal alternative to a routine: `create_watch` with `when: date`, `action: act` and `repeat` (`daily`, `weekdays`, `weekly` with `weekday` 1 Monday to 7 Sunday, `monthly` with `day_of_month` 1 to 31, a shorter month using its last day) at `time` (HH:MM) on the user's clock, in the time zone the reminder was set in, kept across daylight saving changes. Only their user sees them and their conversations; they run with the user's rights at that moment and on the user's AI usage. A recurring reminder does not expire; a user keeps at most 5 active ones within the 20, a paused one aside. The routines clock claims each occurrence by moving the reminder to its next one in the same update, so it stays active and a clock that dies loses no later occurrence; an occurrence missed by more than six hours is skipped, never caught up. Each occurrence is one unattended Numo turn in a conversation of its own, titled with the instruction and the day, under the background guard: no question, no memory write, no reminder change, and in a project with other members only what is the user's. A sensitive action passes only when the user granted its category to this reminder (`grants`: `notification`, `outside_scope`, `pull_request`, `external`, `public_reply`, `trash`, `delete`, `account`, `administration`); memories do not authorize anything there. Without `notification`, a note needs `urgent: true` with a reason. With `administration`, the instance admin tools are offered only if the account is an administrator at that occurrence. `create_watch` with any grant saves nothing: it returns a proposal, the conversation shows a card listing the permissions, and the user's own confirmation (Allow and set reminder) writes the reminder; Numo cannot confirm. `update_watch` pauses, resumes, rewords or moves a recurring reminder, but never one that holds grants (it is replaced through `replaces`, confirmed again) and never its grants. No message announces an occurrence; the turn reports in the journal. An occurrence that does not start or finish, or meets an exhausted usage budget, sends a message; three in a row pause the reminder with a message, and one that finishes clears the count. Settings shows the cadence, the next occurrence, the permissions and the last occurrence with a link to its conversation, with Pause reminder, Resume reminder and Cancel reminder. A routine differs: it belongs to a project, every member sees it and its runs, it runs on the project owner's usage and connections, can start on an event, and never reaches instance administration.
