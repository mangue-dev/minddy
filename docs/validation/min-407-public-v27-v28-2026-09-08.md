## Fresh VM and public attempt

A new isolated Ubuntu 26.04 ARM64 Lima VM, `min407-public-027`, started with no
containers, images, volumes, application configuration, host mounts or forwarded
SSH agent. It has 4 vCPUs, 8 GiB RAM and a 60 GiB sparse virtual disk. Prerequisites
were provisioned before installer timing. The tagged preflight passed.

The v0.10.27 installation started at 15:57:08 UTC and reached health at 16:03:05
UTC: 357 seconds including a test-harness permission correction. All 16 Compose
services became healthy; the last identical installer retry took 59 seconds and
preserved the environment checksum. The local SMTP inbox delivered confirmation
mail. The confirmation callback returned HTTP 500 because sharp could not load
its linux-arm64 native runtime. Public lifecycle acceptance therefore failed.

Two harness/prerequisite observations are separate from that product defect:

- The harness initially cloned public files with umask 077. Kong could not read
  its bind-mounted script. Restoring tracked public files to their Git file
  modes fixed this; no tracked content, secrets or executable flags changed.
- The already-installed pnpm worked, but redundant `corepack enable` attempted
  to write a global yarn shim without permission. The revised procedure checks
  the existing pinned pnpm version instead of modifying global shims.

MIN-506 corrects the Dockerfile's build-platform dependency installation. The
release build previously installed native dependencies on the amd64 builder and
copied them into the ARM64 runtime. Liveness did not exercise that dependency.
Every target image now executes a real native PNG operation before publication.
Existing public tags and digests are preserved.

a text attachment were created through the UI. The downloaded attachment SHA-256
matches the original: `c314b7c37b0649174ba8834fb579baa63a60dff59cc32c82742e716c5a90564b`.

the batch hides that section and its search destination unless billing is configured.

Compiling alongside the full stack exhausted VM memory and reset the test browser.
The services were paused, and 2 GiB of temporary swap let compilation finish.
This is a local build-resource limitation, not a public installation failure.
The synthetic account and data survived; login was repeated from a fresh browser.

The unchanged-environment recovery took 17 seconds. A sealed cold backup preceded
an image update (70 seconds), followed by another cold backup and a blank-storage
restore (61 seconds). Both maintenance checks passed with the scheduler stopped;
ordinary diagnostics passed after reopening. Counts, UUIDs, issue fields, attachment
bytes and revoked-integration 401 responses survived. Fresh password/TOTP login
worked on the restored private HTTP origin. OAuth, protected-resource and MCP
metadata used that new origin with no Minddy Cloud URL.
