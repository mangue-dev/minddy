# MIN-683: instant navigation architecture and measurements

## Decision and scope

Use the existing account-scoped TanStack Query client as the in-memory working
set, prepare complete navigation prerequisites before intent, and preserve
foreground reconciliation. Measure separate renderer and network costs before
changing either. A durable local-first replica is the longer-term architecture
if the measured request/authority gates still prevent the target; it requires
an authorized ordered change log, checkpoint recovery, encrypted device storage,
deletion/access-loss handling and an idempotent optimistic outbox. Adding a second
cache or a longer trust timeout alone does not provide those guarantees.

This document records an incremental program. It does not claim that all
navigation meets 100 ms or that offline use has been implemented.

## Research and historical evidence

Linear's official [delta-sync read-path article](https://linear.app/now/rebuilding-delta-sync-read-path)
describes a local database that serves navigation and issue writes without a
network round trip. A client checkpoint identifies the last applied change;
the server returns ordered actions filtered by access groups and subscriptions.
This supports local reads plus background reconciliation as the target, rather
than server rendering as the explanation for immediate navigation. Its
[scaling talk](https://linear.app/now/scaling-the-linear-sync-engine) is the
official background reference; the linked video has not been transcribed for
this investigation. Specific MobX, IndexedDB, queue and conflict algorithms are
not inferred from the article alone. Minddy does not need Linear's large-scale
serving index to adopt the underlying client/server contract.

Read MIN-614's full issue, implementation plan and comments, and the preserved
[MIN-540 audit](min-540.md) / [navigation audit](min-540-pass2-navigation.md).
The requested wiki Page “Performances de l'app de bureau” is absent from the
current project's wiki map and full-text search. These repository reports are
the available historical record. Prior MIN-614 medians, including 673 ms for
project-to-global activation in phase 3d, are historical measurements, not the
current baseline. MIN-614 is marked done, although its last recorded comments
and plan explicitly retain unmet latency targets and workload gaps.

The existing wiki Page “minddy devient local first” asks for offline data
ownership and self-hosted/local deployment. It is a proposal, not an existing
replication design. Collaboration need not be disabled merely because reads
are local: authorized replication and conflict recovery are required instead.

## Current code and navigation gates

| Layer | Actual owner | Consequence |
| --- | --- | --- |
| Account cache | `lib/account-query-provider.tsx`, `lib/query-provider.tsx` | Query client is remounted by account. Healthy cache freshness uses realtime plus a five-minute age fallback. The disk snapshot is server-sealed, has no device decryption key, and needs an authenticated server opening after restart. |
| Routing | `lib/app-tabs-context.tsx`, `lib/app-tabs-session.ts` | Retained or prepared destinations use the existing history integration. Cold destinations still use Next navigation. The authenticated layout itself does not query workspace content. |
| Code preparation | `lib/app-tab-surfaces.ts` | Dynamic imports are shared by the host and intent preparation; public code readiness alone cannot establish data authority. |
| Intent preparation | `lib/prefetch-tab-destination.ts`, `lib/use-prefetch-project.ts` | Hover/focus starts the existing queries. Project intent warms five reads, but the retained board boundary also needs integrations and saved views. |
| Idle preparation | `lib/pr-tab-preparation.ts`, `AccountTabSync` | One primary missing/invalidated query per visit, only for previously visited destinations. Never-visited open tabs are excluded. No preparation starts while any query is fetching; a streaming poll can delay that opportunity. |
| Retained views | `components/app-tab-view-host.tsx`, `lib/retained-board-data.ts`, `lib/retained-board-read-state.ts` | Weighted bounded Activity retention preserves DOM/state; hidden loaded prerequisites observe shared invalidation. Activation still reconnects effects and can perform style/layout/render work even with zero reads. |
| Issue reads/writes | `components/global-issue-panel.tsx`, `components/issue-side-panel.tsx`, `lib/issue-timeline-queries.ts`, `lib/optimistic/issue-writes.ts` | Card data and writes are optimistic. Comments/events revalidate on every activation with zero stale time. Loaded timeline rows remain visible during refresh; initially missing data, errors and paused reads show a fallback. A visible panel shell is not complete authoritative readiness. |
| Documents | `lib/use-pages-query.ts`, `components/pages/page-view.tsx` | Bodies are separate from tree metadata and excluded from disk snapshots. Explicit preparation grants a short editing-basis window; editor mounting and save/merge/departure semantics must remain intact. |
| Realtime | `lib/realtime-provider.tsx` | Invalidates authorized query keys; it is not an ordered, durable replay log with client checkpoints. Reconnect cannot prove that no event was missed merely from a cached row. |

These are code facts and hypotheses to test, not measured attribution. The
first experiment targets already-open, never-visited project/Page tabs after
idle time. Renderer retention, timeline authority and restart restoration are
separate causes and must not be represented as solved by that experiment.

## Measurement protocol

Baseline product SHA: `738e2bc3fe3317b80e3b625c266234063f41ee68`.
`scripts/performance/measure-instant-navigation.mjs` uses the existing marked,
encrypted MIN-540 fixture: six projects, 600 issues, 120 Pages with 80 blocks,
populated comments, and inert stored forge records. It signs in through the
normal API and reads through authorized application routes. It never reseeds
protected rows, starts agents, copies a personal profile, or changes content.
Temporary UUID-marked tabs are removed; all preexisting tab fields are checked
after cleanup. Failed runs remain in the output and must not enter successful
aggregates.

```sh
npm run build
npm run start -- -p 3111
MINDDY_PERF_LABEL=min683-baseline-web-1 node scripts/performance/measure-instant-navigation.mjs
NODE_PATH=./desktop/node_modules MINDDY_PERF_LABEL=min683-baseline-native-1 node scripts/performance/measure-instant-navigation.mjs --electron
```

Use fresh profiles for each launch. Repeat three native launches and ten warm
observations per primary journey for each retained product candidate. Record
unvisited-tab samples separately from warm returns. Neither warm samples nor
three cold starts establish population-wide startup p95. Keep ordinary runs
separate from CPU profiles and concurrent builds/tests.

The runner records trusted pointerdown to visible active/non-inert DOM, two-frame
paint opportunity, complete-content readiness, long tasks and HTTP timings.
This is lab readiness, not field INP or a direct pixel-presentation timestamp.
Issue shell and authoritative timeline readiness are distinct. Page readiness
requires the populated editor; retained hidden content cannot satisfy it.
Startup covers authenticated navigation through complete board rendering,
excluding credential entry and native executable launch. Every result includes
source SHA, production build ID, browser/native versions and viewport. Raw local
results live under ignored `output/playwright/performance/min683-*`.

## Architecture stages and acceptance matrix

1. Prepare bounded complete destination prerequisites using existing query keys,
   query functions, abort signals and account lifetime. Prioritize visited and
   open tabs, then frequent secondary routes. Schedule behind essential startup
   work; yield to foreground work and avoid unbounded Page/PR bodies.
2. Measure retained activation independently. Optimize only attributed render,
   subscription, layout and effect reconnection costs. Preserve actual controls,
   scroll, focus, filters, selection, drag geometry and hidden remote updates.
3. Make frequently opened issue/Page content ready before intent without
   mistaking a prefetched response for a durable freshness guarantee. Preserve
   failed/paused reads, optimistic rollback, edit overlays and autosave merge.
4. If authoritative activation reads remain the latency floor, add an explicit
   server snapshot/checkpoint protocol and permission-aware deltas. Commit
   change-log entries with data writes; include deletion tombstones, access-loss
   purges, checkpoint expiry/rebootstrap and reconnect recovery. Persist only
   protected records under an explicitly reviewed device-key model. The current
   server-sealed snapshot contract cannot provide offline restart on its own.
5. Add an idempotent durable outbox only with conflict/rebase and ambiguous
   acknowledgement semantics, ordered retries, account isolation and recovery
   UX. Existing optimistic writes remain useful and must not be replaced merely
   to claim local-first behavior.

| Acceptance area | Required evidence | Current state |
| --- | --- | --- |
| Open existing / new tabs, boards and list/kanban | p50/p95, fresh and warm, no common >300 ms | Baseline collection in progress |
| Issues | Shell plus complete description/timeline, optimistic response and persistence/failure | Protocol distinguishes shell/full; writes unchanged |
| Pages | Populated editor/tree, comments, autosave/departure, cold/warm | Baseline collection in progress |
| Secondary routes and submenus | Same before/after scenarios; no shifted cost | Not yet measured |
| Startup | Realistic account, cold/restart, usable ~3 s | Authenticated lab startup only |
| Realtime/permissions/offline recovery | Hidden updates, revocation, logout, missed events and reconciliation | Existing safeguards retained; durable sync remains a design stage |
| Daily feel | User validation of “already ready” | Pending |

and measurement tool change no reader controls or documented product behavior;
no public article, illustration or invented review record is required. This
