## Decision to test

Treat the account's restored tab strip as an explicit working set with complete
read dependencies, rather than a hint for a three-destination idle pass. Keep
the existing account-scoped QueryClient and versioned optimistic writes. Make
readiness, pending preparation and reconciliation separate observable states.
Do not add a second plaintext cache, claim offline support, increase trust
timeouts, or copy another application's sync implementation to establish a
performance result.

## Primary public evidence

### Linear: ordered replication serves local interaction

**Documented facts.** Linear maintains a client database for navigation and
issue writes without a network round trip. Returning clients send the last
applied ordered action ID; the server filters the application-level change log
by access groups and subscriptions. The current serving path separates small
routing metadata from payload enrichment. Recent committed changes remain
authoritative in Postgres despite secondary-index lag; overlapping ranges are
deduplicated, with a Postgres fallback. Shadow comparisons validate action
identity, not just query speed.
[Rebuilding Linear's delta sync read path, August 18, 2026](https://linear.app/now/rebuilding-delta-sync-read-path).

The [official scaling talk page, June 29, 2023](https://linear.app/now/scaling-the-linear-sync-engine)
establishes the talk's authorship and scope. This review has not transcribed its
video and does not derive IndexedDB, MobX, optimistic queue or conflict
algorithms from that page.

**Minddy inference.** Ordered, permission-aware catch-up is a coherent eventual
architecture for immediate local reads. Linear's large-scale serving index is
not justified by Minddy's measured workload. Minddy currently has event-driven
query invalidation, not that replication contract. A warmed QueryClient must
not be described as an equivalent durable local database.

### Notion: cache speed and completeness are different guarantees

**Documented facts.** Notion's browser cache uses WASM SQLite, OPFS, workers and
one elected writer shared across tabs. A first implementation improved navigation
but slowed boot by loading the storage library on the critical path. Loading it
asynchronously removed that startup regression. Slow disk devices also required
racing cache reads with network reads; local storage was not assumed faster.
[How we sped up Notion in the browser with WASM SQLite, July 10, 2024](https://www.notion.com/blog/how-we-sped-up-notion-in-the-browser-with-wasm-sqlite).

**Documented facts.** Notion later strengthened its best-effort cache into a
storage layer that tracks complete page dependencies and independent reasons
for retaining a page. A page can be retained because it was chosen explicitly,
recently visited, or inherited through another page. Removing one reason does
not remove data still needed for another. Downloaded pages receive push
notifications through page snapshot channels. Reconnect compares downloaded
timestamps with server update times and downloads changed pages. The article
mentions CRDT migration but does not specify a complete rich-text merge
algorithm.
[How we made Notion available offline, December 11, 2025](https://www.notion.com/blog/how-we-made-notion-available-offline).

**Minddy inference.** An open tab is a concrete retention/preparation reason,
independent of recent visit history. A cache hit alone cannot prove a complete
document or a writable editing basis. Storage infrastructure must earn its
startup and tail-latency cost before adoption. The existing server-sealed local
snapshot requires authenticated server opening; replacing it with device-readable
content is a separate storage/security design, not a scheduling fix.

### Figma: complete dependency sets, incremental work and optimistic overlays

**Documented facts.** Figma's prototype loader subscribes to a requested subtree
and transitive dependencies, receives a snapshot followed by changes, and
evicts unsubscribed nodes so resubscription receives fresh state. It starts with
the current and reachable frames. Desktop then loads remaining frames in the
background; mobile bounds memory more tightly. Background loads were split into
smaller chunks, and rendering metadata was skipped for unseen content to avoid
main-thread lockups.
[Improving performance with incremental frame loading, January 23, 2024](https://www.figma.com/blog/incremental-frame-loading/).

**Documented facts.** Editable dynamic loading includes both read and write
dependencies. Figma validates partial-loading computations against a shadow
representation with full data. It begins server decode before WebSocket setup
and delays materializing derivable off-page nodes. This is evidence that a
renderable subset and a safe writable subset can differ.
[Speeding up file load times, one page at a time, May 22, 2024](https://www.figma.com/blog/speeding-up-file-load-times-one-page-at-a-time/).

**Documented facts.** Figma document edits apply immediately; incoming
acknowledged property updates must not replace conflicting unacknowledged local
changes. Its documented reconnect procedure downloads a fresh document and
reapplies offline edits. The 2019 document protocol's property-level conflict
semantics do not provide simultaneous rich-text merging. Metadata uses another
system with different tradeoffs.
[How Figma's multiplayer technology works, October 16, 2019](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/).

**Documented facts.** LiveGraph replaced ad hoc metadata events with live query
results driven by the database replication stream. It provides ordered updates,
refetches views after disconnects, checks access on objects and relations, and
integrates optimistic overlays with acknowledgement.
[GraphQL, meet LiveGraph, October 14, 2021](https://www.figma.com/blog/livegraph-real-time-data-fetching-at-figma/).

**Minddy inference.** Prepare complete dependencies and bound background CPU
work. Preserve a local editing overlay until the fresh versioned base is
accepted. Do not transplant Figma's last-property-write protocol into Minddy's
rich-text Pages or assume server hints eliminate editor construction costs.

The retained results in [the main investigation](min-683.md) distinguish repeated

The rejected renewal variants also show that a correct neighboring body can be

those recorded runs. It does not establish that all first Page delays are
network-bound. No independent observations of Linear, Notion or Figma were
performed in this review; their published improvements are not Minddy targets
or comparative benchmark results.

For each stable restored tab, record a dependency inventory at 0, 1, 2 and 3
seconds after renderer bootstrap and immediately before first trusted input:
code readiness; query identity, state, age, invalidation, fetch owner and
payload scope; preparation queue position/budget; editor/surface presence.
Record every missing prerequisite and its initiator. Attribute click-to-usable
time among route wait, request cascade, freshness wait, React work, editor

loading and an immediate real interaction, not only selector presence.

For Page arrivals, specifically distinguish (1) absent body, (2) correctly scoped
accepted cached body blocked by editing-basis freshness, (3) body ready but
editor not yet built, and (4) missing project/tree/mention/permission dependencies.
For PRs, distinguish list/detail and each selected subview's actual contents;
cache readiness does not override GitHub Retry-After or account throttling.

## Concrete staged strategy

1. **Stabilize the workload and instrument ownership.** Verify the Performance
   Tester identity before changing its tabs, retain seven to ten representative
   destinations, and save the exact stable selection. Reuse it across fresh
   profiles and temporary-tab cleanup. Capture executable-to-window and
   renderer-to-usable milestones separately. Keep profiling out of ordinary
   latency runs.
2. **Replace pass coverage with completion coverage.** Build a deduplicated
   dependency manifest for the account's current tab strip through the existing
   factories. Shared project prerequisites have one cache key and owner. The
   active destination gets priority; every restored destination retains its
   pending work until completed, removed, canceled for foreground takeover,
   terminally denied or rate-limited. Limit simultaneous requests and processed
   bytes/work per slice, rather than permanently abandoning entries after three
   destinations. Keep nonessential neighboring suggestions lower priority than
   actual open tabs. Start shared bundle preparation alongside authorized reads,
   yield between meaningful work chunks, and provide a bounded idle deadline.
3. **Complete readiness contracts.** Extend factory coverage only after reading
   the actual foreground consumers for routines, goals, triage and other restored
   views. Test the complete manifest against the consumer's initial prerequisites.
   A readiness flag must name whether it means code, render data, usable controls
   or fresh write basis; one primary query is insufficient for full-content
   certification. Do not eagerly run every PR subview or mount expensive hidden
   editors without measured benefit.
4. **Prototype cached Page rendering with independent write authority.** Permit
   a previously accepted, scoped cached body to seed local display only under
   current account/access guards. Acquire an authorized fresh base in parallel.
   Capture typing into a local draft overlay while this acquisition is pending;
   do not send writes until the fresh base is accepted and a three-way merge
   succeeds. On permission failure remove protected display and preserve only
   the draft under the existing authorized recovery model. On transient failure
   retain the draft and clear feedback. Departure must flush or preserve the
   overlay safely even if acquisition or save is pending. Verify late GETs,
   version conflicts, remote edits, deletions, account disposal and ambiguous
   acknowledgement before removing the current combined gate. Merely showing
   an old editor and enabling writes is not this design.
5. **Keep resume independent of blocking navigation.** Maintain existing error
   recovery and absence/wake catch-up while measuring hidden remote edits on
   boards and Pages. Resume should refresh visible and restored working-set
   dependencies behind retained content, preserve optimistic overlays and revoke
   access immediately when known. Coalesce duplicate wake signals, bound catch-up
   concurrency and distinguish reconciliation completion from UI availability.
   If missing-event recovery remains expensive, design permission-aware version
   checks or an ordered checkpoint protocol before weakening freshness policy.
6. **Earn bootstrap and storage changes with evidence.** If many authorized
   shared reads dominate first usability after manifest completion, prototype an
   account bootstrap response that includes explicit scoped query payloads and
   versions, reusing foreground semantics. Verify response size, server cost,
   permission filtering and identical consumer outputs. If disk recovery or
   serialization dominates, evaluate another protected storage backend with
   account isolation, quota/eviction and a single writer; do not block boot on
   downloading a storage runtime. A durable replica/outbox additionally requires
   checkpoint expiry, access-loss purge, tombstones, ordered retries and conflict
   recovery. That is a distinct architecture stage.

Before each product increment, put its hypothesis, affected prerequisites,
correctness constraints, stable build/fixture IDs and rejection rule into the
issue plan. Compare launch/refresh, every never-activated restored tab, repeated
alternation, direct cross-project Pages, complete PR subviews, immediate typing
and remote-change resume. Reject a candidate that moves startup cost into early
clicks, suppresses loading without useful controls, or regresses another common
destination. The acceptance target remains majority below about 100 ms, no
common journey above about 300 ms, and approximately two to three seconds to
usable launch/refresh, with daily qualitative validation still required.

### Foreground and maintenance ownership

Source inspection explains an admission problem independently of HTTP
duration. `lib/pr-tab-preparation.ts` treats any fetching Query as competing
transport, apart from its own speculative read, successful cached app-tab
reconciliation and a narrow inactive PR auxiliary exception. Such activity
both prevents queue draining and can cancel its current inactive read. The
complete dependency manifest therefore does not imply that work was admitted.
`lib/use-search-index.ts` automatically arms at 1.5 seconds plus an idle
callback, independently of the pending restored manifest. Its measured request
starts while restored dependencies remain missing.

The first narrow experiment should defer automatic search admission until the
listed prerequisites are admitted, while explicit command-palette intent may
bypass that delay. It should permit coexistence with proven passive shell
revalidation rather than disabling those reads. Keep the existing serialized
data lane for attribution. Unknown keys, missing or failed data, active route
reads, explicit overlays, Page write-basis acquisition and foreground takeover
retain priority. A broad exemption for every cached Query is unsupported.

| --- | --- | --- |

| `["me", "triage-counts"]` | Sidebar counts | Passive healthy cached count refresh only. |
| `["me", "smart-assign-warnings"]` | Sidebar assignment indicators | Passive healthy cached refresh only; the endpoint's empty fallback is not an authorization receipt. |

Realtime opens user and project scopes with initial subscription catch-up;
project scopes start after the project list. Those scopes invalidate overlapping

### Server passes and a conditional bootstrap contract

These are source facts, not measured server-span durations. Each protected
endpoint in `lib/server/api-auth.ts` validates claims and then checks live
session/MFA authorization through `auth_authorization_state`. A project route
may subsequently load the living project, check membership and decode project
content through `getProjectAccess`. Page-tree reads then decode each Page's
protected envelope even though the response projects away its body. Search
index likewise decodes protected Page/issue data and resolves members, despite
being a capped search DTO. Key material has a bounded scoped single-flight

The global board can reconcile cycles before data reads, then load its shared
datasets, members and integration references. Project views can create missing
baseline views before listing them. These normal semantics cannot silently be
skipped by a new endpoint. Tab-order additionally reads current user metadata
after authentication. Request duration alone does not attribute time among live
authorization, row retrieval, cold keys, decryption, JSON serialization and
client ingestion; Server Timing or equivalent bounded spans are the next
attribution gate if admission improvements leave the target unmet.

| --- | --- | --- |

bare `setQueryData` promotion would discard those invariants.

A further source review found that the initial prepared Page shortcut also
needed an authority guard. The old intent marker was written before awaiting
the GET, so a canceled newer read could leave a recent cached body marked ready

instead of issuing a GET for a Page not yet created. Neither a cache timestamp
nor an intent marker alone certifies write authority. The regressions exercise
the real conditional mount-refetch path as well as the normal creation and
duplication producers. This guard is a separate candidate from the measured

cache version bump is not upgraded to an authorized receipt by an older GET.

## Autosave handoff after retained-surface resume

The generation fence correctly prevents a retired Page surface from dispatching
another PATCH. A further source review identified a distinct handoff gap: an
already-dispatched PATCH can remain pending while React Activity hides and
resumes the editor. If newly typed content consumes its debounce while joining
that request, the retired operation's finalizer leaves the current draft
pending with no timer. A later acknowledgement or failure does not itself
restore automatic saving. The existing StrictMode regression explicitly
flushed the resumed owner and therefore did not cover this sequence.

Plan task 42 requires a mounted Activity regression without that explicit flush.
When the retired operation settles, only a live resumed surface with a pending
draft and no newer timer may schedule one current-generation attempt. That
attempt retains normal version/conflict processing and failure reporting; its
own failure must not create a timer loop. A disposed account remains unable to
dispatch. A newer input's existing timer and newest body/title must survive
the older operation's completion. This is a correctness prerequisite for the
next candidate build, independent of read-only navigation latency.

## Warm Feedback selection changes the required query scope

The retained scaled candidate's first native ordinary run keeps a material
outlier: its `restored-alternation` Feedback sample paints at 2,003.7 ms, reaches
full content at 1,985.6 ms and records 226 loading frames. The independent CDP
network records establish this sequence relative to that click:

| Ordinary request | Start, ms | End, ms |
| --- | ---: | ---: |
| Unfiltered project Feedback list GET | 0.1 | 1,956.8 |
| Feedback route/RSC GET | 10.5 | 1,430.6 |
| Tab destination PATCH | 1,381.0 | 2,040.7 |
| Another Feedback route/RSC GET | 1,961.8 | 2,125.3 |

Five local-snapshot POSTs overlap this interval. The ordinary network records do
not identify their slots or payloads, so they cannot assign the delay to
query-cache sealing, window-state sealing or encryption. Main-thread work is
approximately 502 ms of task time, including 373 ms of script time; it does not
explain away the nearly two-second list request. The per-sample resource array
is empty, but the independent network records prove that a GET occurred.
Resource timing buffer coverage must not be interpreted as absence of traffic.

The source explains why an apparently warm destination needs a different list.
`FeedbackTeamPage` publishes its selected post through `usePublishCurrentView`.
`AppTabRouteSync` lets only the active owning tab refine its destination, so the
stored tab acquires `?post=`. Both the consumer's `listFilters` and
`feedbackFiltersForDestination` unconditionally choose empty filters for that
parameter. The previously prepared unresolved list has 96 posts under its own
filtered key; the unfiltered 120-post key is a separate ordinary query. The
strict prepared-destination check cannot treat one as the other, and a missing
unfiltered key can send activation through the ordinary Next router.

After the target exists in `posts`, the selection effect consumes `?post=` with
`router.replace`, while the published view continues to preserve the selected
post. The observed route requests are consistent with activation and that
cleanup; the network trace alone does not identify their JavaScript call sites.
The list GET's completion immediately precedes complete content, making it the
observed critical-path wait. Backend contention from overlapping requests is
plausible but unmeasured. The outlier remains part of ordinary results.

A small first experiment could consume this local selection instruction with
native `history.replaceState`, following the Objectives implementation, guarded
by the active route, actual pathname and owning active tab. It must preserve
collection parameters and the published selection, and avoid changing the URL
from a hidden retained view. That removes unnecessary RSC work; it does not
remove the unconditional unfiltered list request or establish a latency win.

A separate bounded intent-resolution design should share one query-scope
selector between the consumer and preparation. When the requested post is
already known in the accepted, correctly scoped current filtered list and still
matches the current state/properties, resolve the selection from that list and
keep its actual filtered key. Never install those 96 rows under the unfiltered
120-post key. A cold, invalidated, denied or unknown target cannot be inferred
absent from a partial or optimistic list. Resolve it with the ordinary protected
post-detail reader, or retain the existing full-list fallback; an archived or
filter-hidden target must retain the existing filter-widening behavior and
obtain the complete ordinary widened collection.

Acceptance provenance needs an explicit review before implementation:
`setQueryData` can make a query successful, and optimistic category edits mutate
list rows. A bare success flag does not prove a requested post was accepted by
the server. Prefer an already accepted ordinary row/detail; otherwise use the
bounded normal detail read. No new permission or write authority follows from
choosing a display query. Tests must cover a real accepted filtered target,
manual-only/pending targets, archived targets outside filters, deletion and
permission failure, cold loading, project isolation, hidden intent cleanup,
selection publication and exact consumer/preparator key agreement. Any change
then needs an isolated identified-build comparison; no proposed saving is a
measured result.
