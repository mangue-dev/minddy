# MIN-540: application performance audit

This document preserves the first-pass findings below. The **second pass** uses
PR #271's starting HEAD, `ec6a12e94235b8c589d86637195ae24dfad28cd6`, as its new
reference; see [the second-pass report](min-540-pass2.md). The **third pass**
starts from `4bc408a59` (the second pass plus its review fixes) and is recorded
in the "Third pass" section below. The old before/after
numbers below are historical and must not be presented as additional gains.

## Scope and workload

The reference revision is `75d8d252d12b3a0264492a21ea588749754da8d8`.
Measurements use a local **production** Next.js server and the real authenticated
APIs/database, with a separate marked test account. No personal account data is
copied. The deterministic workload contains six projects, 600 issues with
descriptions/plans, 120 Pages of 80 blocks, 1,200 issue comments, 480 Page comments,
and 180 stored PR records across six inert repository links.

PR records represent previously synchronized history. The fixture has no forge
credentials: list performance is measured, but GitHub/GitLab latency, live diffs,
webhooks, and real synchronization are outside these measurements. No paid agent,
routine, invitation, or mail workflow is started. The seed only inserts missing
rows, checks ownership and inertness on reuse, and never resets existing data.

## Prioritized findings and changes

| Priority | Cause | Change |
| --- | --- | --- |
| P0 | Every inactive issue card mounted `border-beam`, injecting a stylesheet and observers. The 600-card board had over 600 stylesheets; opening an ordinary menu spent hundreds of milliseconds recalculating styles. | Keep the card wrapper mounted; mount the existing beam overlay only when active and through its fade-out. Preserve child DOM, input value, focus, halo styling, and reduced motion. |
| P0 | Updating the assistant's ambient issue context notified all cards even though they only use stable action callbacks. | Split the action context from panel state and migrate action-only consumers. A regression test counts renders for 600 consumers. |
| P0 | A prepared Page could become “not ready” after the ten-second prefetch TTL on an unrelated render, unmounting its editor into a spinner. | Capture prepared readiness for the lifetime of that mounted Page. A newly mounted expired Page still revalidates; remote reconciliation stays intact. |
| P0 | `IssueContextMenu` omitted its portal on the server but inserted it in the first client render, even when closed. React reported hydration mismatch #418 and regenerated the surrounding shell. | Attach the portal after hydration; preserve its existing pointer placement, keyboard handling, and close/focus lifecycle. A real server-render/hydrate test asserts that surrounding DOM survives. |
| P1 | Sidebar and topbar animated layout widths; tab resize observers and page layout ran during the transition. Secondary lists lost their portal target during exit-before-entry animations. | Apply the final reserved width once; retain transform/opacity transitions. Keep secondary portal targets mounted, preserve list state/scroll, and make hidden content inert. |
| P1 | Tab persistence/list status broadcasts reached shell, boards, palette, and sidebar consumers. Desktop also constructed mobile palette models. | Separate stable tab session/navigation contexts from the strip snapshot. Gate mobile models by viewport and prepare desktop palette models during its existing warm-up. |
| P1 | TanStack's persistence subscriber dehydrated the whole cache on every cache event, even for excluded polls. Throttling the storage writer happens too late to prevent this work. | Filter unchanged/excluded data events and coalesce dehydration, serialization, and storage into one bounded idle task. Cancel pending saves on logout; preserve restore, quota failure, paused-mutation, and hidden-page behavior. |
| P1 | Root `:has(.app-shell)` selectors repeatedly matched the application subtree, including portaled menus. | Use an equivalent lifecycle attribute with matching specificity and cleanup when leaving the shell. |
| P2 | Successful comment writes waited for another GET to become visible; ordinary Page text edits rebuilt block membership and regrouped comments. | Publish the acknowledged comment response immediately, cancel older reads, reconcile in the background, preserve hydrated attachment fields/newer edits, and retain block-set identity when membership is unchanged. |
| P2 | Board integrations were fetched after member resolution even though only project IDs are needed. | Fetch independent members and integrations concurrently after the access-scoped project read. |

Existing optimistic issue writes, undo, pending-write overlays, realtime
invalidation, Page autosave/merge, drag geometry caching, diff virtualization, and
route/data prefetch remain in use. A second navigation cache would need separate
freshness, memory, account, and unsaved-document semantics; it would not address
the measured CSS and context propagation costs.

## Reproducing measurements

Prerequisites: normal runtime environment, service role for the explicitly marked
fixture only, `CAPTURES_DEMO_PASSWORD`, and installed Playwright Chromium.

```sh
node scripts/performance/seed.mjs
node scripts/performance/seed.mjs --apply
npm run build
npm run start -- -p 3111
# In another terminal, without a concurrent build or test run:
MINDDY_PERF_LABEL=before node scripts/performance/measure.mjs
# Build and restart the changed application, using the same account:
MINDDY_PERF_LABEL=after node scripts/performance/measure.mjs
node scripts/performance/cache-benchmark.mjs
```

The browser runner creates a fresh context, sets the dedicated account's two
benchmark tabs, declines analytics, and uses a 1440×1000 viewport, normal motion,
and no CPU/network throttle. It measures cold board load, sidebar hide/show,
issue opening, context menu, creation dialog, pointer drag/drop, tab navigation,
prefetched Page opening, Page menu/comments, comment submission, and PR list.
The comment it creates is removed afterwards. Dragging is reversed. It records
browser/build IDs, API response statuses, long tasks, animation-frame gaps,
Event Timing entries, stylesheet counts, storage work, and CDP script/layout/style
durations under ignored `output/playwright/performance/`.

Set `MINDDY_PERF_BASE_URL` to another local port and `MINDDY_PERF_BUILD_DIR` to
that server's build directory to measure an independent reference checkout.
The final reference server was built from an archive of the revision above;
both servers were exercised by the same measurement script. The runner targets
the first visible issue card, so the exact card can change after drag ordering
changes; all fixture cards have the same description/plan sizes and comment count.
Run `MINDDY_PERF_LABEL=visual node scripts/performance/measure.mjs --visual` for
active/inactive halo screenshots and a DOM-identity assertion. That mode injects
only the browser's activity response and never starts a real agent.
Use `MINDDY_PERF_LABEL=mobile node scripts/performance/measure.mjs --mobile` for
a 390×844 Chromium Page/comments layout smoke check; it is not a mobile-device
performance benchmark.

`readyMs` is automated action-to-ready latency, including Playwright dispatch,
the explicit visible-state condition, and two animation frames. It is a lab
comparison, **not field INP**. The 350 ms observation tail captures animation and
immediate follow-up work. Navigation across documents uses absolute performance
time origins; CDP counters reset for the new document. Three repetitions are
collected for common board and tab interactions. Cold loads and remote writes
are sensitive to network/server variance; individual timings must not be
presented as universal service latency.
Scoped CSS selectors avoid measuring Playwright's accessible-name traversal of
every button on the 600-card board. Earlier exploratory runs using broad role
selectors were discarded; the committed samples use the same scoped selectors.

## Research informing the implementation

- [Linear's delta sync read path](https://linear.app/now/rebuilding-delta-sync-read-path)
  and [sync engine scaling](https://linear.app/now/scaling-the-linear-sync-engine)
  explain local reads and reconciliation. Minddy already has optimistic local
  state; the measurements prioritize removing redundant work in that system.
- [TanStack render optimizations](https://tanstack.com/query/latest/docs/framework/react/guides/render-optimizations)
  and [request waterfalls](https://tanstack.com/query/latest/docs/framework/react/guides/request-waterfalls)
  support narrow subscriptions and independent requests.
- [React memo](https://react.dev/reference/react/memo) explains why a memoized
  component still renders when its context changes. Splitting stable actions is
  necessary here; adding another `memo` around a card would not solve it.
- [Next.js navigation](https://nextjs.org/docs/app/getting-started/linking-and-navigating)
  covers router caching and intent prefetch. Existing Page preparation is retained,
  with its lifetime bug corrected instead of simply increasing a stale timeout.
- [Chrome selector statistics](https://developer.chrome.com/docs/devtools/performance/selector-stats)
  and [MDN `:has()` performance](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has#performance_considerations)
  guide the style-recalculation investigation and bounded root selectors.
- [Browser animation guidance](https://web.dev/articles/animations-guide) favors
  transform/opacity where possible. GPU compositing cannot fix JavaScript
  broadcasts, synchronous storage, or excessive CSS matching. No blanket
  `will-change`, forced layers on every card, or Electron acceleration flags are
  introduced; the browser can composite the retained sidebar slide.
- [INP](https://web.dev/articles/optimize-inp),
  [long tasks](https://web.dev/articles/optimize-long-tasks), and
  [idle scheduling](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback)
  distinguish input, processing, presentation, and deferrable persistence work.

## Remaining independent work

- Tab hover/focus prefetch and smaller metadata requests for tab labels: open
  tabs currently share full Page/objective lists and selected PR detail queries.
- Board virtualization beyond this workload: all cards retain keyboard, search,
  drag targets, and inline controls. Any windowing must preserve those behaviors.
- Server query plans, RLS costs, and payload projection at larger account sizes;
  this pass does not invent database indexes without query-plan evidence.
- Live forge synchronization/diffs, paid agent streams, native Electron GPU
  tracing, Safari/mobile hardware, slow networks, and multi-user concurrency
  deserve separate controlled runs. Headless Chromium cannot establish smoothness
  on every device or equivalence with Linear.

credentials. Values below are milliseconds rounded to the nearest integer.
Repeated interactions use the median of three runs, except the two warm issue
opens; other rows are single samples.

The prepared Page's editor disappeared after the ten-second TTL in the reference
and survived the identical interaction after correction. Screenshots confirm
that the Page content and activity panel remain visible together. The active
agent halo retains its appearance and fades away while keeping the exact card
element mounted; inactive cards retain their layout, content, and controls.

The idle board has **7 stylesheets instead of 607**. Median style recalculation
for the issue menu fell from 692 ms to 6 ms, with its longest task falling from
705 ms to none over the 50 ms threshold. Dragging still produces long tasks:
their combined duration fell from 2,766 ms to 1,170 ms. The board still mounts
all 600 rich cards, so this change does not establish instant navigation or
smooth dragging on every device. Sidebar work can still exceed one frame.

The isolated cache benchmark performs 300 excluded polling updates and 100
comment edits. Cache-wide synchronous scans/snapshots fell from **401 to zero**
during that task, followed by **one deferred snapshot**. Across ten runs after
three warm-ups, median bookkeeping time fell from 13.26 ms to 0.31 ms. Its no-op
storage deliberately isolates subscription/dehydration work; these are neither
physical storage-write counts nor browser interaction latencies.

Comment changes publish the authoritative POST/PATCH response without waiting
for a second GET. They do not speculate before acknowledgement. The browser
submission metric measures acknowledgement and draft clearing, so it cannot
quantify the removed second-read delay. Regression tests verify immediate cache
publication, older-read cancellation, attachment preservation, newer-write
ordering, and deletion behavior.

## Third pass (hardware/compositing, network efficiency, main-thread blocking)

Reference: PR #271 HEAD `4bc408a59` (second pass + review fixes). Same dedicated
fixture, same measurement protocol, no concurrent build or test workload during
timed series. The runner in `scripts/performance/measure.mjs` now records one
CDP Network entry per request (connection setup, server wait, decoded size)
for every measured interaction and for the cold load, exposes Event Timing
probes (`inpMs` with its input/processing/presentation split) for real
interactions, and adds a wheel-scroll probe over the 600-card board. Medians
below are from the paired three-repeat series `pass3-before`/`pass3-after`
(production builds `B1t7fDAiCyMXd9aBektVT` and `dfkXx16K4EiPEr93nHNwI`,
Chromium 153, Apple M4 Pro). Cold loads and remote writes stay
network-sensitive single samples; they are not service-latency claims.

### Findings and changes

- **Shell-level `:has()` invalidation sets dominated every interaction that
  changed style mid-tree.** `app/globals.css` matched the hidden-sidebar state
  through `.app-shell:has([data-sidebar-hidden="true"]) ...` and
  `body:has([data-sidebar-hidden="true"]) ...`. A `:has()` anchored that high
  attaches descendant-watching invalidation sets to those ancestors, so any
  style-relevant change under them re-evaluated the whole workspace.
  DevTools-timeline tracing showed every sidebar toggle, dialog open, and
  scroll gesture running one full ~27,600-node style recalculation
  (108–116 ms per pass); a drag window spent 478 ms of style work and 639 ms
  of long tasks on it. `SidebarNavOverlay` now syncs a lifecycle attribute
  onto `<body>` and the shell main, and the rules read that attribute
  directly with the same specificity (hydration keeps the docked snapshot,
  the same trade the visibility preference already makes).
- **The cold load read the full issue set twice.** The initial realtime
  catch-up fired the global issue snapshot whenever the aggregate board had
  an observer, including when the board query was still pending — the
  measured cold load fetched `/api/me/board` (1.33 MB) and `/api/me/issues`
  (1.33 MB) back to back. The snapshot now fires only for a board that
  already carries data (the missed-broadcast gap it exists to close);
  reconnect/resume paths are unchanged.
- **The issue side panel constructed its rich editor inside the opening
  gesture.** Tiptap view construction is a long synchronous task; the panel
  now paints with the existing fallback that mirrors the committed markdown
  in the same typography and swaps the editor in two frames later. The
  visual contract is unchanged and drafts survive close/reopen; a real
  browser check verified the mirror, the swap, and draft retention.
- **GET /api/pull-requests read its sweep states and rows serially.** The two
  reads are independent and now run together; a never-swept repository still
  forces its blocking forge scan and a re-read of the rows, so a first
  display still shows the synchronized PRs. The row-read server wait fell
  from 529 ms (before) to 389 ms (after); the page-level marker stays
  network-dominated (see "What did not move").

### What did not move, and why (with tracing evidence)

- **The initial catch-up wave.** On a cold start the user-scope subscription
  fires a coalesced invalidation that refetches eight mounted small endpoints
  (`billing`, `billing/usage`, `notifications`, `projects/invitations`,
  `pull-requests/count`, `views`, `triage-counts`, `app-tabs`) whose data is
  under a second old. The wave is the correctness net for the window between
  each read's start and the channel's delivery: their GETs left ~440 ms
  before the subscription delivered, so a write in that window is missed by
  both the response and the live channel. Skipping it would trade a rare
  missed update for six fewer requests; a delta-sync read path (Linear-style)
  is the real fix and stays separate work.
- **Payload projection on the board cache.** The aggregate payload is 1.33 MB:
  0.63 MB description text, 0.23 MB plan text, and ~0.45 MB of per-row
  columns/JSON structure. Cards only need `description.slice(0, 400)` and a
  plan progress count, but the side panel sows its editor from the same
  cached row — shipping truncated text would feed the description editor
  truncated content, and per-issue refetches would move the wait into the
  panel. The second navigation cache that could separate those consumers was
  rejected in the second pass for freshness/memory/unsaved-document reasons.
- **Tab return to a Page (~280 ms ready).** CPU profiles attribute most of
  the reconnect script time to ProseMirror `updateStateInner` — the retained
  editor re-applies its state when its Activity view resumes. Not changed:
  the editor state legitimately changed while hidden (autosave reconciliation),
  and suppressing the update risks stale documents.
- **Warm issue open's remaining task (~250 ms).** In-page instrumentation
  shows Radix's modal `ariaHideOutside` writing `data-aria-hidden`/`aria-hidden`
  to ~616 elements per dialog open. It is the library's a11y mechanism for
  modal dialogs over an app whose DOM holds in-tree RSC scripts and live
  regions; `modal={false}` would remove it but also removes the focus trap
  and outside-content hiding — a behavior change, not an optimization.
- **PR list ready marker (~947 ms).** The route's row-read wait fell by
  ~140 ms, but the marker waits for the cross-document navigation (477 KB
  HTML plus chunk hydration) and the shell's own first-read set; the page
  shows the list only after all of it. No live-forge latency is involved in
  this fixture.
- **HTTP caching (ETag/If-None-Match, Cache-Control) was evaluated and not
  shipped.** These endpoints are account-scoped JSON responses whose server
  cost is the RLS reads themselves; computing a trustworthy ETag requires the
  same reads, so a 304 saves transfer (~10 ms locally, ~1.3 MB on `/all`
  refetches) but not the server work, and no cheap freshness token exists for
  aggregates that mix members (auth admin API), relations, objectives and
  cycles. The duplicated reads were removed at the source instead. Revisit
  with a server-side change token if cold/warm refetches become the
  bottleneck at larger account sizes.
- **Board windowing was not attempted.** The pass-2 constraint stands: every
  keyboard, search, drag-target and inline-control behavior must be provably
  preserved first. This pass's scroll and drag results (no long tasks,
  3 ms of style work) lower the urgency rather than raising it.
