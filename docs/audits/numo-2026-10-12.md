# Numo audit — 2026-10-12

Comparison of Numo's surface (`lib/server/assistant/**`, especially
[prompt.ts](../../lib/server/assistant/prompt.ts) and
[tools.ts](../../lib/server/assistant/tools.ts)) with the application's actual
implementation. Seven findings: one blocking mismatch, three behavior drifts,
and three cosmetic inconsistencies. All seven are addressed in this branch.

The audit compared both implementations rather than relying on comments or
names, and re-verified the shared enums behind the tool schemas (issue
statuses, priorities, efforts, recurrence cadences, plan task states, relation
types, objective statuses, trash types, view sorts and facets, feedback
statuses, webhook events and scopes, cycle preferences, sandbox regions and
sizes, themes, send shortcuts, Numo landing statuses, scratchpad cap, locales)
against their defining modules. Tool behaviors were checked one by one against
their executors: issue reads and writes, plan patching, pages, feedback, project
and account settings, integrations and webhooks, trash, cycles, scratchpad,
routines, pull requests, code-agent launches, worker mediation, MCP setup and
`ask_user`.

The findings describe the audited tree at
[d5c2d862](https://github.com/mangue-dev/minddy/commit/d5c2d862).

## Blocking mismatch

### 1. Project auto-assignment is advertised although nothing implements it

**Original guidance:** `update_project`'s `auto_assign_enabled`
([tools.ts](../../lib/server/assistant/tools.ts)) said "Assign a newly created
issue to whoever created it, for everyone on this project."

**Actual behavior:** the column is written
([update-project.ts](../../lib/server/update-project.ts):83-85) but read
nowhere — no server or client code assigns issues because of it. The only
working auto-assignment is the account-level `auto_assign_created`
preference, applied at creation time
([create-issue-dialog.tsx](../../components/create-issue-dialog.tsx):264). The
setting exists only in the creation wizard, whose copy says "Assigns you the
issues you create in this project"
([messages/en.json](../../messages/en.json):2867-2868) — a third, different
wording.

**Effect and correction:** Numo could flip a project flag and promise behavior
that never happens. The field description now states what the setting actually
is: stored by the wizard, with no effect on its own, and points at the
account-level preference that does the work.

## Behavior drift

### 2. `merge_pull_request` claims to re-check red or running CI locally

**Original guidance:** the tool said "The tool re-checks all three and
refuses", and the block comment claimed the executor
([pull-request-writes.ts](../../lib/server/assistant/pull-request-writes.ts))
"re-checks all three before calling the forge".

**Actual behavior:** the executor re-checks merged, closed, draft and conflict
states locally (pull-request-writes.ts:229-259) and deliberately leaves
required checks to the forge's branch protection, because the aggregate checks
summary also contains optional jobs (comment at :260-263;
[pull-request-writes.test.ts](../../lib/server/assistant/pull-request-writes.test.ts):254).
With no required-check protection, the forge accepts a merge despite a red
check.

**Effect and correction:** Numo believed a red CI always blocks its merges, so
it could report a refusal that never comes. The description and the comment now
say that draft and conflicts are re-checked locally while the red-CI part
belongs to branch protection, and that a red or running check must be honored
by Numo even where the forge would accept it.

### 3. The trash prose omits wiki pages

**Original guidance:** `move_to_trash`, `list_trash` and `restore_from_trash`
([tools.ts](../../lib/server/assistant/tools.ts)) and the shared rules
([prompt.ts](../../lib/server/assistant/prompt.ts):277-281) enumerated
"issues, objectives, feedback posts, routines and projects".

**Actual behavior:** `TRASH_TYPES` includes `"page"`
([trash.ts](../../lib/server/trash.ts):54-69); the tools' `type` enums spread
it, so pages are already offered to the model; page deletion and restoration
run through the trash
([trash.ts](../../lib/server/trash.ts):243-246, 597-600;
[route.ts](../../app/api/projects/[id]/pages/[pageId]/route.ts):97), and a page
under a trashed project fails to restore like the other types.

**Effect and correction:** Numo read prose saying pages are not trashed while
its own tool enum offered them. All four enumerations now include wiki pages,
and `restore_from_trash` mentions a page comes back with its subpages.

### 4. The `duplicate` status and `duplicate_of_id` were paired only in guidance

**Original guidance:** the vocabulary block
([prompt.ts](../../lib/server/assistant/prompt.ts):99), the shared status field
and `update_issues` ([tools.ts](../../lib/server/assistant/tools.ts)) stated
that `duplicate` requires `duplicate_of_id`; `create_issue` even required it
despite exposing no such parameter.

**Actual behavior:** only `triage_decision` enforced the pair
([execute-tool.ts](../../lib/server/assistant/execute-tool.ts):2661-2668).
The update core accepted `status: "duplicate"` with no target and validated the
target only when it was provided
([update-issue.ts](../../lib/server/update-issue.ts):224-227, 338-342), and the
creation core accepted a `duplicate` landing status although no creation
surface can pass a target
([create-issue.ts](../../lib/server/create-issue.ts):231-233) — every UI
duplicate gesture passes the target
([triage-page.tsx](../../components/triage/triage-page.tsx):410), so only a
violating write could produce the dangling state.

**Effect and correction:** the claimed invariant did not exist server-side.
The update core now refuses a `duplicate` status without a call-provided
target, the creation core refuses `duplicate` as a landing status (new
`duplicateRequiresTarget` message in the six catalogs), and `create_issue`'s
status description says a new issue cannot be born a duplicate. Regression
tests cover both refusals in
[tenancy-refs.test.ts](../../lib/server/tenancy-refs.test.ts).

## Cosmetic inconsistencies

### 5. Webhook refusal on feedback keys overstated

**Original guidance and correction:** `update_integration_webhook` said a
'feedback' key "has no webhook and this is refused on one"
([tools.ts](../../lib/server/assistant/tools.ts)), while
[integrations.ts](../../lib/server/integrations.ts):206-224 refuses only
ENABLING on such a key — disabling one left over from an earlier setup stays
possible, as its own comment documents. The description now matches.

### 6. `notif_page` omitted page comments

**Original guidance and correction:** the toggle description mentioned only
page mentions and agent writes
([tools.ts](../../lib/server/assistant/tools.ts)), while the page category also
covers `page_comment` — someone commenting on a page the user wrote or on a
thread they took part in
([notification-prefs.ts](../../lib/notification-prefs.ts):116-119;
[page-comments.ts](../../lib/server/page-comments.ts):182-186). The description
now lists all three triggers.

### 7. `set_scratchpad` presented `expected_rev` as always enforced

**Original guidance and correction:** the description said "ALWAYS pass
expected_rev … the write is rejected instead of clobbering the user's
concurrent edits" ([tools.ts](../../lib/server/assistant/tools.ts)), but the
executor writes anyway when the field is omitted — the compare-and-swap applies
only when it is passed
([execute-tool.ts](../../lib/server/assistant/execute-tool.ts):3807-3820; the
MCP twin documents the same optional contract, mcp/tools.ts:3339-3343). The
description now states the real contract: a stale `expected_rev` is rejected,
omitting it overwrites unconditionally.

## Verified without divergence

The checked surface matched the code on, among others: issue reads
(`get_issue`'s relations, resources, sub-issues and `linked_feedback`),
plan patching (`append_to_plan`, `update_plan_tasks`, `edit_issue_text`),
propose_backlog, invitations, integrations and their usage contract, views and
the locked personal view, feedback status lifecycle and public replies, account
settings and their notification toggles, cycles and the fill engine, trash
retention and ownership, scratchpad task surgery, routines (schema, ownership,
runs, occurrences, budget), pull-request reads, linking, management and
reviews, `launch_code_agent`'s modes and required fields, worker mediation,
MCP setup and OAuth attempts (~10 minutes, single-use), the wiki map limit,
`get_help` topics (the four alias ids resolve) and `ask_user`'s client card.
