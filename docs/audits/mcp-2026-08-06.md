# Audit MCP — 2026-08-06

Confrontation of the MCP surface (`lib/server/mcp/**`, `app/api/mcp/**`,
`app/.well-known/mcp/**`, `app/(marketing)/mcp/**`) to the actual application code.
8 findings: 1 blocking, 5 drifts, 2 cosmetic.

Method: reading on both sides, no observation based on a comment or a name.
The 41 recorded tools were reread one by one against their core business, and the
prose enumerations against their constants.

> **The 8 findings are corrected in this same PR** (the audit was first delivered alone,
> then the requested corrections). Each section keeps the report as it was established,
> with the line numbers from BEFORE correction, and ends with what was done.
> Summary at the end of the document.

**What is healthy, and worth saying**: `/llms.txt`, `/llms-full.txt` and the
server are derived from the actual record via `catalog.ts` — no possible drift from
this side. The public page `/mcp` no longer lists tools and therefore does not lie about anything. The
ticket enumerations (statuses, priorities, efforts), recurrence rates,
webhook events and scopes, plan task states, and integration genres
are all imported from their source. Access guards (`requireProject`, owner-only on
integrations and the board) correspond exactly to those of the API routes
equivalent, and no tool bypasses a control. The MIN-196 review (comments
public) has been reflected in `tools.ts`.

## Bloquant

### 1. Plan outcome limit is returned to the agent as a database failure

**What the MCP announces** — nothing, and that's the problem: `minddy_create_issue` returns a
error code `database_error` with message the bare string `issueLimitReached`.

- [lib/server/mcp/tools.ts:173-186](../../lib/server/mcp/tools.ts) — `coreFail` does not know
  only three cases: `404 → not_found`, `400 → invalid_params`, **all the rest →
  `database_error`**. The message is `rawMessage ?? errorKey ?? "Request failed"`, and the
  `params` of the heart are discarded.
- [lib/server/mcp/tools.ts:1179](../../lib/server/mcp/tools.ts) — `if (!result.ok) return coreFail(result)`.

**What the application does** — it is a definitive refusal, at 403, with the limit in the
message:

- [lib/server/create-issue.ts:143-154](../../lib/server/create-issue.ts) — `ensureIssueLimit`
  raises a `PlanLimitError`, converted to `{ status: 403, errorKey: "issueLimitReached",
  params: { limit } }`.
- [lib/server/plan-limit-error.ts:22-23](../../lib/server/plan-limit-error.ts) — `status = 403`.
- [app/api/v1/issues/route.ts:149-165](../../app/api/v1/issues/route.ts) — the public API
  renders `403 issue_limit_reached` with the limit, and the comment specifically says
  why: “Returning it to 500 said “try again” to a customer who would never have been able to
  succeed — he tried endlessly, and no one learned the real cause. »
- [app/api/projects/[id]/issues/route.ts:87-90](<../../app/api/projects/[id]/issues/route.ts>) —
  the app route returns `result.status` (so 403) and the message localized with `params`.

**Why it's blocking** — the MCP is the only one calling for this heart to fall back into the
gotcha that API v1 explicitly fixed. An agent who fills the backlog of a project
free sees `database_error`, deduces a transient failure, and tries again; he can neither
explain it to the user or stop. The limit itself, which the heart nevertheless has
calculated, never reaches him.

**Fixed** — `coreFail` takes `params` and processes `403` (`plan_limit_reached`) and `409`
(`conflict`) before its default mapping. A `CORE_MESSAGES` table translates the `errorKey`
that the MCP can actually return — today `issueLimitReached`, with the limit and a
“retrying will not help” explicit. The same message is sent by `coreMessage(...)` in the
`failed` tables per ticket (sub-tickets of `minddy_create_issue`, `minddy_update_issues`,
`minddy_add_to_cycle`, `minddy_remove_from_cycle`), which lost the same information.

## Drifts

### 2. An agent reads feedback in a language the team no longer reads

**What the MCP returns** — `minddy_get_feedback` constructs its response field by field:
`title`, `body`, `submitted_title`, `submitted_body`, `status`, `vote_count`, `is_public`,
`source`, `author`, `linked_issue`, `comments`.

- [lib/server/mcp/tools.ts:2633-2653](../../lib/server/mcp/tools.ts).

**What the app does** — from automatic translation, the team view displays
by default the **translation**, with an original/translated toggle:

- [supabase/migrations/20261107090000_feedback_translation.sql](../../supabase/migrations/20261107090000_feedback_translation.sql) —
  adds `source_language`, `translated_title`, `translated_body`, `translated_language`.
- [lib/server/feedback/posts.ts:69-75](../../lib/server/feedback/posts.ts) and
  [posts.ts:81-82](../../lib/server/feedback/posts.ts) — the columns are in
  `FEEDBACK_POST_SELECT`, therefore already loaded by `getTeamFeedbackDetail`.
- [components/feedback/feedback-team-page.tsx:1417-1421](../../components/feedback/feedback-team-page.tsx) —
  the team view prefers the translation when `translated_language` is the language of
  the team.

The MCP is the TEAM channel (it renders the real identity of the author, the comments
internal): he should read what the team reads. Today an agent sorting a return
written in Portuguese for a French team receives Portuguese, while the translation
is already in base, next to it, free to return.

**Fixed** — all four columns are rendered as `minddy_get_feedback`, and its description
says the reading rule: the translation is NEXT to the original (let the board continue
to display), `translated_language` says what language it is in, and that is what we read
when it matches that of the team — exactly what the team view does.

### 3. No MCP tool can change the status of a return — and the core keeps a setting for a missing caller

**What the MCP can do** on feedback: read it, promote it to a ticket, link it /
unlink it, leave an internal note, respond publicly.

**What the app does** — any member changes title, body, `status`,
`is_public` and `review_state`:

- [app/api/projects/[id]/feedback/[postId]/route.ts:28-66](<../../app/api/projects/[id]/feedback/[postId]/route.ts>) —
  `PATCH`, keeps `requireProjectMember`.
- [lib/server/feedback/posts.ts:288-340](../../lib/server/feedback/posts.ts) —
  `updateFeedbackPostFields`, whose signature still bears
  `mcpKeyId`: "Assigns the action to the MCP agent (via_mcp + key) in the thread." A
  parameter which only exists for an MCP caller, and no longer any MCP caller.

The dropout trace is in the file: `updateFeedbackPostFields` is still
imported by [tools.ts:53](../../lib/server/mcp/tools.ts) and is never called there again —
MIN-196 ([879fdae](https://github.com/mangue-dev/minddy-issues/commit/879fdae)) reconnected
`minddy_respond_feedback` to `addCommentToFeedbackPost` and left the import behind.
An agent can therefore promote a return as a ticket but not mark it `declined`, not the
mark `spam`, not post a feedback stuck in the review queue.

**Fixed** — `minddy_update_feedback` (status, `is_public`, `review_state`) branch
`updateFeedbackPostFields` with the `mcpKeyId` which awaited it: the import becomes alive again,
and the activity thread names the agent key like everywhere else.

With **the team view lock**, which is not in the core: the status of a linked return
to a ticket is copied from this ticket by `status-sync` at each transition, and the file
team makes it read-only for this reason
([feedback-team-page.tsx:1423-1429](../../components/feedback/feedback-team-page.tsx)).
The tool therefore refuses a `status` on a linked return (`status_follows_issue`) and returns to
`minddy_update_issues` — accepting it would have offered the agent a gesture that the next
transition of the ticket would have been crushed, that is to say one more drift, created by the
correction.

### 4. The server manual still describes the pre-MIN-196 comment thread

**What the MCP announces** — [lib/server/mcp/instructions.ts:68-69](../../lib/server/mcp/instructions.ts):

> `minddy_list_feedback` / `minddy_get_feedback` read them (**the latter includes the
> internal, team-only comment thread**)

**What the app does** — the thread has two visibility from the comments
public:

- [supabase/migrations/20261109090000_feedback_public_comments.sql](../../supabase/migrations/20261109090000_feedback_public_comments.sql) —
  `comments.visibility` (`internal` / `public`), visiting author, and the team response
  become a thread entry.
- [lib/server/mcp/tools.ts:2600-2605](../../lib/server/mcp/tools.ts) — the description of
  the tool is up to date: “Each comment carries a `visibility` … including the
  replies visitors wrote there. »

The server therefore contradicts itself: the instructions read during initialization say
“team-only”, the tool says the opposite. MIN-196 hit `tools.ts` and not `instructions.ts`.

**Fixed** — parenthesis now says ENTIRE thread (internal notes and responses
public visitors, each marked by its `visibility`) and translation; the
paragraph announces `minddy_update_feedback` and the fact that a linked return no longer carries its
status; `minddy_configure_feedback_board` is described as opening or closing tokens
public comments, in addition to publishing the board and making the secret SSO.

### 5. The status `spam` has existed for two months and the MCP does not name it anywhere

**What the MCP announces** — [lib/server/mcp/tools.ts:2561-2563](../../lib/server/mcp/tools.ts):

> title, public status (**open/planned/in_progress/shipped/declined**), vote_count …

**Ce que l'application fait** — il y a six statuts :

- [lib/feedback/types.ts:14-21](../../lib/feedback/types.ts) — `FEEDBACK_POST_STATUSES`
  includes `spam`.
- [supabase/migrations/20261106090000_feedback_spam_status.sql](../../supabase/migrations/20261106090000_feedback_spam_status.sql) —
  `review_state = 'rejected'` is folded into the status under the name `spam`.

The Zod schema is derived from the constant ([tools.ts:2568](../../lib/server/mcp/tools.ts))
and therefore accepts `spam` ; `listTeamFeedback` does not filter anything and **makes returns spam**
in the default list. A model who has only read the description does not know the value
exists, nor that it can filter it, nor how to read those it receives. (Same wording
outdated on the Numo side, [lib/server/assistant/tools.ts:737-738](../../lib/server/assistant/tools.ts) —
the drift is shared, not specific to MCP.)

**Fixed** — description lists all six values ​​and says what `spam` means. And
because a prose enumeration is not linked to anything, a test now holds it:
[catalog.test.ts](../../lib/server/mcp/catalog.test.ts) loops over
`FEEDBACK_POST_STATUSES` and requires each value to be in the description — a
seventh status will no longer be able to be added silently. The formulation of Numo, outside the scope
of this audit, remains to be repeated.

### 6. The MCP does not allow you to know if a return is actually on the board

**What MCP renders** — `minddy_list_feedback` maps `id`, `title`, `status`,
`vote_count`, `is_public`, `source`, `linked_issue_id`
([tools.ts:2583-2591](../../lib/server/mcp/tools.ts)); `minddy_get_feedback` adds the
body and thread, without `review_state` either
([tools.ts:2633-2653](../../lib/server/mcp/tools.ts)). The description says "whether it's
public”.

**What the application does** — public visibility depends on three conditions, written
black and white in migration:

- [supabase/migrations/20261106090000_feedback_spam_status.sql:17-18](../../supabase/migrations/20261106090000_feedback_spam_status.sql) —
  `board visible ⇔ is_public and review_state = 'published' and status <> 'spam' and merged_into_id is null`.
- [lib/feedback/types.ts:167](../../lib/feedback/types.ts) — `FEEDBACK_REVIEW_STATES`
  (`pending` = waiting for the AI review, invisible from the board even if public).
- `review_state` is loaded by `FEEDBACK_POST_SELECT`: it is already there, just not rendered.

A `pending` return and a published return are therefore indistinguishable for an agent, who can
respond publicly (`minddy_respond_feedback`) on feedback that no one sees
again, or announce to the user that a request is "on the board" when it is
in queue.

**Fixed** — `review_state` is rendered by both tools, and the description of
`minddy_list_feedback` writes the rule in full: visible ⇔ `is_public` AND
`review_state` = `published` AND `status` ≠ `spam`, with the so-called consequence (“a post
`pending` hasn't been seen by anyone yet, don't tell the user their request is
online").

## Summary

| --- | --- | --- | --- |
| 1 | Blocking | Plan boundary rendered as `database_error` | `coreFail` processes 403/409 and carries `params`; `coreMessage` also covers `failed` per ticket |
| 2 | Drift | returns never returned translation | 4 columns rendered by `minddy_get_feedback` + reading rule in description |
| 3 | Drift | Status of a non-modifiable return; import dead | New `minddy_update_feedback` tool, with the “status followed by ticket” lock |
| 4 | Drift | `instructions.ts` describes the thread before MIN-196 | Rewritten feedback paragraph (whole thread, translation, new tool, `allow_comments`) |
| 5 | Drift | `spam` missing from descriptions | Six values ​​written, **and a test that loops on the constant** |

| 7 | Cosmetics | Goal statuses copied | `z.enum(OBJECTIVE_STATUS_VALUES)` |

Four of the first six findings relate to feedback: this is where all
the migrations of the last two months (`spam_status`, `translation`, `voice`,
`public_comments`), and the MCP surface followed for public comments — not for the
remains.

**What the corrections change for an MCP client**: one more tool
(`minddy_update_feedback`, 42 total), three new stable error codes
(`plan_limit_reached`, `conflict`, `status_follows_issue`), and added fields — never
removed — on both readings of the feedback. `/llms.txt`, `/llms-full.txt` and the card of
server follow by themselves: they are replayed from the actual recording.

**What remains open**, outside the scope of this audit: Numo has the same listing
expired return statuses
([assistant/tools.ts:737-738](../../lib/server/assistant/tools.ts)), the same dead import of
`updateFeedbackPostFields` ([execute-tool.ts:110](../../lib/server/assistant/execute-tool.ts)),
and the comment from [app/api/projects/[id]/feedback/[postId]/route.ts](<../../app/api/projects/[id]/feedback/[postId]/route.ts>)
still says that the heart is “shared with the Numo respond_to_feedback tool”, which is not
no longer true since MIN-196.

**Found in review of this PR, and fixed with it** — the `status` filter of
`minddy_list_feedback` (prior to the audit) applied to the window of 500 lines that
`listTeamFeedback` returns, not query. This window is ordered BY VOTES: the
statuses which do not collect any — `spam` first, the one that observation 5 has just made
requestable — are exactly those that the ceiling cuts. On a project of more than 500
returns, `status: ["spam"]` therefore returned an empty list while the base had the response,
and silently. `listTeamFeedback` now takes `statuses` which it applies in
`.in("status", …)` ; the two callers who filtered in JS after the fact — the MCP and
[Numo's `list_feedback`](../../lib/server/assistant/execute-tool.ts), same code — the
pass to him. The third caller (the team view route) does not filter and change
no behavior.

**Verification** — `npm run typecheck` green, `npx vitest run` green (148 files,
1,917 tests), including three new cases in
[lib/server/mcp/catalog.test.ts](../../lib/server/mcp/catalog.test.ts) which connect the
descriptions feedback to their constants.
