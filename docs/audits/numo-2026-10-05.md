# Numo audit — 2026-10-05

Comparison of Numo's surface (`lib/server/assistant/**`, `app/api/assistant/**`,
`components/assistant/**`, `lib/assistant-*.ts`) with the application's actual
implementation. Six findings: one blocking mismatch, three behavior drifts, and
two cosmetic inconsistencies. All six are addressed in this branch.

The audit compared both implementations rather than relying on comments or names.
Tool enums (issue statuses, recurrence cadences, plan task states, cycle intensities,
webhook events, trash types, automation presets, themes, keyboard shortcuts, and
sandbox settings) come from shared application modules and were checked individually.
The account and project settings implementations match `update_account_settings`
and `update_project`, including `automation_start_delay_minutes` mapping to
`automation_start_delay_min`.

The findings describe the audited tree at
[95b0496c](https://github.com/mangue-dev/minddy/commit/95b0496c).

## Blocking mismatch

### 1. Invitations incorrectly require an existing account and rule out email delivery

**Original guidance:** `invite_member` in
[tools.ts](../../lib/server/assistant/tools.ts) required an existing account and
said that no email was sent.

**Actual behavior:** [members.ts](../../lib/server/members.ts) accepts an
invitation even when the address does not resolve to an existing account
(MIN-197). The pending invitation can be associated with the account after signup
with that verified address. When transactional email is configured,
`sendInvitationEmail` runs after the response through `afterOrNow`.
[project-members.tsx](../../components/project-members.tsx) displays matching
copy from [messages/en.json](../../messages/en.json).

**Effect and correction:** Numo could refuse a valid invitation or deny email
delivery. The tool now accepts any valid address, explains where the pending
invitation appears after signup or signin, and describes email as best-effort
delivery when configured. Otherwise, delivery is limited to the in-app invitation.

## Behavior drift

### 2. Project settings advertise retired AI Smart Triage and overstate tool coverage

**Original guidance:** `update_project` claimed to cover every settings switch
and advertised an AI scoring pass gated by plan or budget.

**Actual behavior:** [smart-triage.ts](../../lib/smart-triage.ts) accepts only
`rules` after MIN-642. The field description was corrected, but the enclosing
tool description was not. [update-project.ts](../../lib/server/update-project.ts)
has no plan or budget gate for `smart_triage_mode`; Smart Assign and automations
retain their gates. The icon picker in
[project-general-section.tsx](../../components/settings/project-general-section.tsx)
uses the [icon route](../../app/api/projects/[id]/icon/route.ts) for file upload,
`site_url`, and deletion, but Numo has no corresponding tool.

**Effect and correction:** Numo could offer a retired engine, describe an
inapplicable refusal, or promise unsupported settings changes. The description
now lists supported settings, identifies Smart Triage as rules-only, limits
plan and budget gates to Smart Assign and automations, and directs icon changes
to Settings → General.

### 3. Four unused comment prompt builders contradict the shared runtime

**Original code:** [prompt.ts](../../lib/server/assistant/prompt.ts) contained
`buildCommentSystemPrompt`, `buildObjectiveCommentSystemPrompt`,
`buildPageCommentSystemPrompt`, `buildFeedbackCommentSystemPrompt`, and their
`CommentPrompt*` interfaces. They prohibited follow-up questions; the feedback
builder also imposed a 1,000-character reply limit without headings.

**Actual behavior:** No production code calls those builders after the shared
comment conversation integration (#205, 8d7309be) and caller removal (a1ea001d).
[comment-agent.ts](../../lib/server/assistant/comment-agent.ts) allows blocking
questions through `ask_user`, and later replies resume the same durable work.
[turns.ts](../../lib/server/numo/turns.ts) assembles `buildSystemPrompt` or
`buildGlobalSystemPrompt`, both of which include distress guidance.
[tools-contract.test.ts](../../lib/server/assistant/tools-contract.test.ts)
already rejects the obsolete feedback restrictions; the comment limit in
[add-comment.ts](../../lib/server/add-comment.ts) is 65,536 characters.

**Effect and correction:** There was no current runtime effect, but the unused
instructions could mislead future prompt changes. Removed the four builders
and their interfaces. The updated
[prompt-distress.test.ts](../../lib/server/assistant/prompt-distress.test.ts)
covers both active builders and explains how shared comment surfaces inherit
their distress guidance.

### 4. Saved-view guidance omits the default smart sort and sort direction

**Original guidance:** The prompt listed `manual | priority | created | updated |
due` and claimed to cover every toolbar facet.

**Actual behavior:** [views.ts](../../lib/server/views.ts) includes `smart` as
the default. [board-toolbar.tsx](../../components/board-toolbar.tsx) exposes all
six sorts and directional sorting through `display.sortDirection`. The tool
schema already exposes both settings.

**Effect and correction:** Numo could overlook the default sort or direction
control. The prompt now includes `smart`, identifies it as the default, and
documents `display.sortDirection` as `asc | desc`.

## Cosmetic inconsistencies

### 5. Feedback status guidance omits spam

**Original guidance:** The `list_feedback` description listed `open`, `planned`,
`in_progress`, `shipped`, and `declined`, although its enum includes `spam`.

**Actual behavior and correction:** [feedback/types.ts](../../lib/feedback/types.ts),
[feedback-team-page.tsx](../../components/feedback/feedback-team-page.tsx), and
[team-queries.ts](../../lib/server/feedback/team-queries.ts) support spam in
team-side filtering. The public board excludes it. The description now lists
all six statuses and explains this visibility distinction.

### 6. The personal system view is described using a fixed French name

**Original guidance:** The prompt and `list_views` description identified the
`kind: "my"` view using its French name.

**Actual behavior and correction:** The
[views route](../../app/api/projects/[id]/views/route.ts) seeds the name using
`tBoard("myView")`: “My issues” in English and “Mes tickets” in French, from the
locale catalogs. Both descriptions now identify the name as localized. The
locked name, locked `["@me"]` assignee filter, and deletion protection remain.
