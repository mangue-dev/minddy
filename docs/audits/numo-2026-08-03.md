## Bloquant

### 1. Numo states that nothing can be deleted; the application has trash since MIN-133

**What Numo says** — the same sentence in all four prompts:

- [lib/server/assistant/prompt.ts:194](../../lib/server/assistant/prompt.ts) — “You can NEVER
  delete issues, views, objectives, categories or projects. To discard an issue, set its
  status to 'canceled' (and say so). »
- Repeated in [prompt.ts:454](../../lib/server/assistant/prompt.ts) (ticket comment),
  [prompt.ts:555](../../lib/server/assistant/prompt.ts) (objective),
  [prompt.ts:648](../../lib/server/assistant/prompt.ts) (feedback).
- [prompt.ts:143-144](../../lib/server/assistant/prompt.ts) — “Categories, like
  issues/views/objectives, are never deleted. »
- [tools.ts:805](../../lib/server/assistant/tools.ts) — description of `update_category`:
  “(Categories cannot be deleted.)”
- [tools.ts:19-20](../../lib/server/assistant/tools.ts) — “No delete tools anywhere —
  cancellation goes through status changes. »

**What the app does** — delete exists everywhere, and it's reversible:

- [supabase/migrations/20260919090000_soft_delete_trash.sql](../../supabase/migrations/20260919090000_soft_delete_trash.sql) —
  soft delete tickets, objectives and feedback (the projects already had it), 30 days
  in trash then purge.
- [app/api/issues/[id]/route.ts:75](<../../app/api/issues/[id]/route.ts>) — `softDeleteItem("issue", …)`.
  Same as [objectives/[id]/route.ts:65](<../../app/api/objectives/[id]/route.ts>) and
  [projects/[id]/route.ts:63](<../../app/api/projects/[id]/route.ts>).
- **Hard** deletion for views and categories:
  [app/api/views/[id]/route.ts:42](<../../app/api/views/[id]/route.ts>),
  [app/api/categories/[id]/route.ts:60](<../../app/api/categories/[id]/route.ts>).
- User trash: [app/api/me/trash/route.ts](../../app/api/me/trash/route.ts) (list,
  empty) and [app/api/me/trash/[type]/[id]/route.ts](<../../app/api/me/trash/[type]/[id]/route.ts>)
  (restore, purge).
- The group action on the board is literally called “Move issue to trash”
  ([messages/en.json:459](../../messages/en.json)).

**Consequence** — “delete this ticket” cancels the ticket instead of putting it on
trash: two different gestures (one remains on the board in `canceled`, the other in
comes out and catches up in 30 days), and Numo describes the app as it no longer exists.

**Fixed** — three tools plugged into `lib/server/trash.ts`, which already carries its own
access controls: `move_to_trash`, `restore_from_trash` and `list_trash`
([tools.ts](../../lib/server/assistant/tools.ts), execution in
[execute-tool.ts](../../lib/server/assistant/execute-tool.ts) — `executeTrashTool`). They are
cross-projects, therefore stored in `ACCOUNT_TOOLS`. The permanent purge is **not** exposed:
it does not catch up, and the night sweeping does it anyway after 30 days —
what Numo can do remains reversible.

The rule is rewritten in the four prompts: delete and cancel are two gestures
different, do the one requested, confirm before putting in the trash. Views and
categories don't have a trash bin and Numo doesn't have a tool to delete them — it says so
which rather than “nothing is deleted”.

### 2. `read_pull_request` queries `agent_runs` when the source of truth is `pull_requests`

**What Numo does** — [execute-tool.ts:886-897](../../lib/server/assistant/execute-tool.ts):
the PR of a ticket is searched in `agent_runs` (`.from("agent_runs")` … `.not("pr_number","is",null)`),
and failing that the tool returns “This issue has no pull request opened by the code agent yet. »

**What the app does** —
[supabase/migrations/20260922090000_pull_requests.sql:1-17](../../supabase/migrations/20260922090000_pull_requests.sql):
“A HUMAN PR has no run: it literally had no place to exist.” The
table `pull_requests` has become the source of truth for the state of a PR, powered by
webhooks and scans, attached to the ticket by convention (`issue_id`).

- [lib/server/agent/pr-link.ts:92](../../lib/server/agent/pr-link.ts) — `link_pull_request` writes
  `pull_requests.issue_id`, never `agent_runs`.
- [components/pull-requests/pull-requests-page.tsx:160-172](../../components/pull-requests/pull-requests-page.tsx) —
  the page pushes `prNumber` into the Numo context for **any** PR; `runId` is there
  nullable (`selected.runId ?? undefined`).
- [prompt.ts:672](../../lib/server/assistant/prompt.ts) — the context block then says:
  “To read or explain what it changes, call read_pull_request with the issue id above. »

**Consequence** — three paths fail while the user sees the PR on the screen: one PR
human, a PR attached by convention (identifier in the branch, “Fixes KEY-42”), and
a PR that Numo himself has just attached with `link_pull_request`. The two PR tools of
Numo are not talking about the same table.

**Fixed** — new function `findPullRequestForIssue`
([pull-requests.ts](../../lib/server/agent/pull-requests.ts)): the live PR of the ticket, at
most recently hit defect at the forge — the same order as the Pull Requests page, for
that “this PR” means the same thing on both sides. `read_pull_request` leaves from there and does not
falls back on `agent_runs.pr_number` only for the rows before the table. The error message
no longer talks about the agent, and the tool description explicitly says that it also reads a PR
human or attached by convention.

## Drift

### 3. Relationships between tickets (MIN-25) are invisible to Numo

**Numo side** — the vocabulary only knows `parent_id` and `duplicate_of_id`
([prompt.ts:55](../../lib/server/assistant/prompt.ts)); the description of `get_issue`
([tools.ts:208](../../lib/server/assistant/tools.ts)) lists what it renders — “all fields,
categories, comments…, sub-issues, and the duplicate target if any” — **without citing the
relations**, which the answer nevertheless contains
([lib/server/issue-reads.ts:412-442, 465](../../lib/server/issue-reads.ts)). No tools
write to `ASSISTANT_TOOLS`.

**Application side** — three types to choose from in the UI (`blocks`, `blocked_by`, `related`):
[lib/relation-constants.ts:40](../../lib/relation-constants.ts),
[components/relations-section.tsx](../../components/relations-section.tsx). The MCP server,
him, already exposes the writing: `minddy_link_issues`
([lib/server/mcp/tools.ts:1559](../../lib/server/mcp/tools.ts)). And `fill_cycle` announces to
Number that “blocks relations are respected” ([tools.ts:1003](../../lib/server/assistant/tools.ts))
— an invariant of which he can neither read nor pose the cause.

**Corrected** — `link_issues` tool (set or remove a relationship, idempotent on both sides),
connected to `addIssueRelation` / `removeIssueRelation` / `findIssueRelation` with
`viaAssistant: true`, and both ends checked in the draft of the conversation. The
relationships enter the vocabulary of the prompt (with what distinguishes them from a subticket and
of a duplicate, and their effect on cycle filling) and the description of `get_issue`
finally announces what she was already giving back.

### 4. Project settings: Numo knows three out of seven

**Numo side** — `update_project` only exposes `name`, `key`, `color`
([tools.ts:729-747](../../lib/server/assistant/tools.ts)), and the prompt repeats it
([prompt.ts:142-143](../../lib/server/assistant/prompt.ts): “update_project (name, key,
accent color)").

**Application side** — [lib/server/update-project.ts:75-140](../../lib/server/update-project.ts)
also accepts `auto_assign_enabled`, `smart_assign_enabled`, `smart_assign_rules`,
`automations_enabled`, `automations`, `feedback_review_enabled`,
`feedback_review_skip_over_budget`. All editable by hand:

- Smart Assign: [components/settings/smart-assign-section.tsx:46](../../components/settings/smart-assign-section.tsx)
  (`updateProject(project.id, { smart_assign_enabled })`), rules per member l. 59-63.
- Automations: [components/settings/account-automations-section.tsx:192](../../components/settings/account-automations-section.tsx)
  (`updateProject(projectId, { automations_enabled })`).
- Feedback AI review: [components/project-feedback-settings.tsx:522-552](../../components/project-feedback-settings.tsx).

And the project settings page explicitly invites you to use Numo:
[app/(app)/projects/[id]/settings/page.tsx:392](<../../app/(app)/projects/[id]/settings/page.tsx>)
with “Ask Numo to change your project settings…” ([messages/en.json:1741](../../messages/en.json)).

**Fixed** — `update_project` exposes all seven settings (`auto_assign_enabled`,
`smart_assign_enabled`, `smart_assign_rules`, `automations_enabled`,
`feedback_review_enabled`, `feedback_review_skip_over_budget` in addition to name/key/color) and
returns their state after writing. The two entitlement refusals (`smartAssignNotAllowed`,
`automationsNotAllowed`) now have a readable phrase that Numo relays instead of displaying
a key. Automation RULES (`automations`, structure `quand … si … alors`) remain
deliberately outside the diagram: the preset lives on account, it is the switch which decides

### 5. Account settings: automations, notifications and out-of-scope agent preferences

The account page displays “Ask Numo to change your settings…”
([app/(app)/settings/page.tsx:139](<../../app/(app)/settings/page.tsx>),
[messages/en.json:1404](../../messages/en.json)) above ten tabs. Numo covers it
three (profile, preferences, cycles). Three shortcomings verified:

**has. Automation preset** — `automation_preset` is in rendered type and **returned** to
Numo ([lib/server/account-settings.ts:59, 89](../../lib/server/account-settings.ts)) and the
heart knows how to write it (l. 169-177), but: it is absent from the diagram of `update_account_settings`
([tools.ts:907-977](../../lib/server/assistant/tools.ts)) *and* missing from `CHANGEABLE` list
([account-settings.ts:220-234](../../lib/server/account-settings.ts)) — a call that only
this field therefore fails on “No account settings to update. » before writing anything.
The UI writes it directly by `updateUserMetadata`
([account-automations-section.tsx:59-63](../../components/settings/account-automations-section.tsx)).
Numo reads a setting it cannot change, and its description of `get_account_settings`
([tools.ts:900](../../lib/server/assistant/tools.ts)) doesn't mention it.

**b. Notifications (MIN-82)** — five toggles in `user_metadata`, same mechanics as
cycles: [lib/notification-prefs.ts:10-37](../../lib/notification-prefs.ts), written by
[account-notifications-section.tsx:46-48](../../components/settings/account-notifications-section.tsx).
Neither read nor written by Numo.

**c. Agent preferences** — default model **and reasoning level**:
[app/api/account/agent-preferences/route.ts:33-48](../../app/api/account/agent-preferences/route.ts),
picker [components/agent/reasoning-combobox.tsx](../../components/agent/reasoning-combobox.tsx).
The word “reasoning” does not appear anywhere in `lib/server/assistant/`:
`list_agent_models` only returns `default_model`
([execute-tool.ts:524](../../lib/server/assistant/execute-tool.ts)) and `launch_code_agent`
has no matching parameter ([tools.ts:1312-1339](../../lib/server/assistant/tools.ts)),
while the launch route accepts it by run
([app/api/issues/[id]/agent/route.ts:130](<../../app/api/issues/[id]/agent/route.ts>)).

**Fixed** — in [account-settings.ts](../../lib/server/account-settings.ts):
`AUTOMATION_PRESET_META_KEY` enters `CHANGEABLE` (without it, a call carrying only the
preset came out as “nothing to change” even though the block that wrote it had just set it), the
five notification toggles are read and written like cycles, and agent preferences
— only account setting that lives in `user_agent_preferences` and not in `user_metadata` —
are read separately and written by upsert, with the SAME validation as the PUT of the route,
model ceiling of the plan included (refusal returns the model, its multiplier and the ceiling,
so that Numo can come up with another one). The `update_account_settings` schema exposes the
eleven corresponding fields; `launch_code_agent` takes a `reasoning_level` for a run
given and returns the run one.

### 6. Twelve unlabeled tools in Numo's feed

`TOOL_META` ([components/assistant/tool-call-display.tsx:139](../../components/assistant/tool-call-display.tsx))
has no entry for: `list_integrations`, `list_feedback`, `get_feedback`,
`promote_feedback_to_issue`, `link_feedback_to_issue`, `unlink_feedback`,
`respond_to_feedback`, `list_agent_models`, `launch_code_agent`, `read_pull_request`,
`link_pull_request`, `list_global_filter_options`.

The fallback is generic: icon `LayoutGrid` and label `processing` / `done`
([tool-call-display.tsx:655-679](../../components/assistant/tool-call-display.tsx)). The same
fallback applies to live @Numo comment (`toolRunningLabel`, l. 664-668). No key
corresponding name does not exist in the namespace `ToolCall` of
[messages/en.json](../../messages/en.json) / [messages/fr.json](../../messages/fr.json) — this
is therefore not a missing translation but a pair of strings never written.

Concretely: launch the code agent, read a PR or promote feedback are displayed
“Processing…” then “Done”, when creating a category is displayed by its name.

**Fixed** — the 12 missing entries plus the 4 new tools, with their 54 keys
written in both catalogs with the same gesture. Some wording says what the result
really tells rather than a generic: a `launch_code_agent` which lands on a run already
in progress displays “message sent to agent” and not “agent started”, and a response
public emptied displays its removal, not its publication.

So that the drift does not return, [tool-labels.test.ts](../../lib/server/assistant/tool-labels.test.ts)
pins the contract: each tool of the two modes has its entry in `TOOL_META`, and each key
that a request label exists in `en.json` **and** `fr.json`. A tool added without its line
makes the rest blush instead of displaying “Processing…” in production.

### 7. Feedback Board: Numo reads options it cannot adjust

`get_feedback_board` announces to make “the display options”
([tools.ts:585](../../lib/server/assistant/tools.ts)) and effectively makes `show_categories`
and `show_views` ([lib/server/feedback/board-config.ts:74-75](../../lib/server/feedback/board-config.ts)).
`configure_feedback_board` only offers `enabled` and `generate_sso_secret`
([tools.ts:592-609](../../lib/server/assistant/tools.ts)).

On the application side, the PATCH of the board settings (owner) writes `show_views`,
`show_categories`, `visible_view_ids`, `accent_light`, `accent_dark`, and knows how to run the
token like clear SSO secret
([app/api/projects/[id]/feedback/settings/route.ts:7-17, 104-120](<../../app/api/projects/[id]/feedback/settings/route.ts>)).

**Fixed** — `configureFeedbackBoard` accepts all three display options (written on a
existing board, otherwise `boardNotFound`), and `getFeedbackBoardConfig` also renders
`visible_view_ids`: Numo can reread what he has just set. The rotation of the token and
Clearing the SSO secret remains out of reach — they break a living integration.

### 8. Two enumerations copied by hand into `tools.ts`

The file imports its domain values ([tools.ts:3-15](../../lib/server/assistant/tools.ts):
statuses, priorities, efforts, cadences, task states, cycle intensities, statuses of
feedback, local) — except two:

- objective statuses written hard in `create_objective` and `update_objective`
  ([tools.ts:492, 522](../../lib/server/assistant/tools.ts)) while
  [lib/objective-constants.ts:26](../../lib/objective-constants.ts) exports
  `OBJECTIVE_STATUS_VALUES` ;
- hard-written view sorts ([tools.ts:430, 465](../../lib/server/assistant/tools.ts)); here the
  constant `VIEW_SORTS` exists but is not exported
  ([lib/server/views.ts:51](../../lib/server/views.ts)), you should export it first.

The values ​​coincide today — it is the drift mechanism, not yet the drift.

**Fixed** — `VIEW_SORTS` is exported from [views.ts](../../lib/server/views.ts) and imported.
For goal statuses and relationship types, the list of values has moved into two
modules without dependency — [objective-validation.ts](../../lib/objective-validation.ts) and
[relation-validation.ts](../../lib/relation-validation.ts), twins of
`lib/issue-validation.ts` — and icon modules re-export them. `tools.ts` now reads
its four enumerations at the source, without pulling lucid into the server bundle.
