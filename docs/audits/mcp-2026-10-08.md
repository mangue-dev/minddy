# MCP audit — 2026-10-08

Comparison of the external MCP surface (`lib/server/mcp/**`, `app/api/mcp/route.ts`,
`app/.well-known/mcp/server-card.json`, `app/(marketing)/mcp/**`) with the
application's actual implementation. Four findings: no blocking mismatch, two
description drifts (both published to `/llms.txt` and the MCP server card through
`lib/server/mcp/catalog.ts:64`), and two cosmetic inconsistencies. All four are
corrected on this branch.

The audit read both sides instead of trusting names or comments. Verified clean:

- **Schemas vs real contract** — every enum in the MCP schemas imports the shared
  application constants (`ISSUE_STATUSES`, `ISSUE_PRIORITIES`, `ISSUE_EFFORTS`,
  `PLAN_TASK_STATES`, `RECURRENCE_CADENCES`, `OBJECTIVE_STATUS_VALUES`,
  `FEEDBACK_POST_STATUSES`, `FEEDBACK_REVIEW_STATES`, `WEBHOOK_EVENTS`,
  `WEBHOOK_SCOPES`), so no enum could drift; the DB CHECK constraints
  (`supabase/migrations/20270106090000_baseline.sql:3469-3473`) and the default
  status `backlog` (`:3442`) match the advertised defaults.
- **Handler → core signatures** — every core called by a handler was checked
  (`createIssueForProject`, `updateIssueFields`, `appendToPlan`, `setTaskState`,
  `editIssueText`, `createObjective`/`updateObjective`, `addCommentTo*`,
  `setScratchpad`/`mutateScratchpad`/`applyScratchpadTaskChanges`,
  `getCycleOverview` (`which: "previous"` supported),
  `moveIssuesBetweenCycles`, feedback team queries, `listIntegrations`,
  `createRoutine`/`updateRoutine`/`deleteRoutine`, `readInboxNotifications`,
  page tools). No ignored argument, no changed semantics.
- **Access control** — no MCP tool bypasses a check its HTTP route applies.
  Owner-only tools (`configure_feedback_board` `tools.ts:4531`,
  `create_integration` `:4693`, `configure_webhook` `:4776`,
  `revoke_integration` `:5126`) match their owner-only routes
  (`app/api/projects/[id]/feedback/settings/route.ts:112`,
  `app/api/projects/[id]/integrations/route.ts:40`,
  `app/api/projects/[id]/integrations/[integrationId]/route.ts:21`,
  `app/api/projects/[id]/integrations/[integrationId]/route.ts:61`); routines
  enforce owner-only in the shared core (`lib/server/routines.ts:236,338`), the
  same core the routes use. Deliberately stricter, not a divergence:
  `minddy_configure_webhook` refuses to set the delivery destination
  (`webhookHumanOnly`), which the owner-facing route allows (MIN-341).
- **Recent schema** — the last two months of migrations contain no MCP-relevant
  drift: only additions, and the three touched contracts
  (`link_pull_request_to_issue_atomic`, `search_pages`,
  `touch_oauth_grant_activity`) stay compatible with the MCP paths.
- **Public docs** — `/llms.txt` and `/llms-full.txt` and the server card replay

## Description drift

### 1. `minddy_get_pull_request` claimed a GitHub-only prerequisite

**Published description:** the tool "fails ... if the project has no linked
GitHub repo" ([tools.ts:1161](../../lib/server/mcp/tools.ts) before this fix).

**Actual behavior:** the handler resolves the project's git link and builds the
forge by provider — GitHub and GitLab both work
([forge.ts:708-710](../../lib/server/agent/forge.ts),
[repo-providers.ts:40-51](../../lib/repo-providers.ts)). The sibling tool
`minddy_link_pull_request` already documents GitLab merge requests
(`'!42'`, `tools.ts:1343`). An agent wiring a GitLab project would believe the
read tool is unavailable.

**Fix:** the description now says "no linked repository (GitHub or GitLab)".

### 2. `minddy_list_objectives` described a raw done/total progress

**Published description:** progress "computed from linked issues (status 'done'
/ all linked)" ([tools.ts:1454](../../lib/server/mcp/tools.ts) before this fix).

**Actual behavior:** the handler counts `done` over every closed status (done,
canceled, duplicate) and computes `percent` effort-weighted with partial credit
by status ([tools.ts:1509-1539](../../lib/server/mcp/tools.ts)), mirroring the
UI bar (`lib/use-objectives-query.ts`, effort points from
[issue-constants.ts:60-66](../../lib/issue-constants.ts)). A canceled issue also
settles the objective; the old wording said it did not.

**Fix:** the description now states both rules (closed statuses, effort-weighted).

## Cosmetic

### 3. Module header described the surface of several months ago

The header comment of [tools.ts:169](../../lib/server/mcp/tools.ts) still said
the surface was "projects (reading), tickets (+ plan), objectives, comments"
with "no deletions". The registered surface now also covers the inbox, pages,
resources, scratchpad, cycles, the feedback board, integrations and routines —
and `minddy_delete_routine` does trash one thing. Rewritten in line with what
`registerMinddyTools` registers.

### 4. `/llms.txt` called the cycle a fortnight

The object model of [llms.txt](../../app/llms.txt/route.ts) said "**Cycle**:
the key owner's personal, cross-project fortnight" (`:131`). Cycles are a week
or a fortnight (`durationWeeks: 1 | 2`,
[lib/cycle-prefs.ts:24-25](../../lib/cycle-prefs.ts)); `instructions.ts` already
said "week/fortnight". Aligned to "week/fortnight".

## Questions raised by the Numo comparison (no divergence found)

Comparing `lib/server/assistant/tools.ts` (84 core tools) with the MCP surface
(59 tools), the asymmetries below look deliberate — the reduced-surface rule is
stated in the module header and the docs — but are recorded here as the
questions they deserve:

- Numo-only write surfaces absent from MCP: views, trash (except routines),
  member and category management, project settings, automations, PR management
  (`merge_pull_request`, `update_pull_request`, `post_pull_request_comment`,
  `resolve_pull_request_threads`), `propose_backlog`, `launch_code_agent`.
- MCP-only tools Numo lacks: `minddy_add_objective_comment`,
  `minddy_add_page_comment`, `minddy_get_project`, `minddy_get_resource`,
  `minddy_update_feedback` (Numo reaches the same results through other tools).
- One Numo message may be stale, outside this audit's scope:
  `lib/server/assistant/execute-tool.ts:363` still says "The code agent
  currently supports GitHub repositories only", while the run plumbing mentions
  GitLab webhooks (`lib/server/agent/runs.ts:2008`). Worth its own check.
