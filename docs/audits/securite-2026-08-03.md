## Constats

### 1. Colonnes de tokens de `git_user_identities` lisibles via PostgREST — **faible**

`supabase/migrations/20260924090000_git_user_identities.sql:35-38` and `:58`

The table (MIN-144) has `access_token_encrypted` and `refresh_token_encrypted` —
the *user-to-server* token of the GitHub App under which human gestures are carried out
on a PR. Its reading policy is proprietary (`user_id = auth.uid()`), and
his comment states that "token columns are NEVER returned by
the API”.

This is **exactly** the reasoning that `20260926090000_security_grants.sql` has
was written to correct two days later, on six other tables: a policy
RLS filters ROWS, not COLUMNS. `git_user_identities` arrived before
this lock and was never added to the list.

**Scenario.** Any logged in user has the public anon key
(it is in the bundle) and its JWT. He calls directly
`GET https://<ref>.supabase.co/rest/v1/git_user_identities?select=access_token_encrypted,refresh_token_encrypted`
and obtains the AES-256-GCM wrapper of its own GitHub token. Not the token in
clear — the key is `GIT_TOKEN_ENCRYPTION_SECRET`, server side — but encrypted
exfiltrated does not retract: it remains usable the day this key leaks, and
a stolen XSS or JWT results in a durable copy.

**Fixed** — `supabase/migrations/20261006090000_git_user_identities_grants.sql`:
`revoke select` table-level then re-grant from the white list, in the form
exact of the other six tables. No effect on behavior: the six readings
applications in this table all go through customer service, and `PUBLIC_COLS`
already only cites whitelisted columns.
**⚠ The migration must be applied in production** for the report to be closed.

### 2. The public PR attachment bucket serves the MIME type chosen by the client — **weak**

`lib/server/agent/pr-actions.ts:1311` (before fix)

`prAttachmentResponse` uploads to `forge-attachments` — bucket **public in
reading**, on purpose: the URL goes into a comment at the forge and must remain
readable by GitHub and its email notifications. The `contentType` was taken as
which of `file.type`, that is to say from the client.

**Scenario.** A user creates an account, a project, links a repository to it which he
control, open a PR, then
`POST /api/pull-requests/<prId>/attachments` with a file announced in
`text/html`. It gets a public, stable, non-expiring URL under the domain
of our Supabase project, which **opens as a page** — a page of
phishing hosted in our name. Same in `image/svg+xml`, which executes its script
when reached by direct navigation (and not in a `<img>`).
The gatekeeper to the PR, which is there, decides WHO can write; she doesn't say
nothing THAT is served.

**Fixed** — whitelist `INLINE_SAFE_ATTACHMENT_TYPES` (png, jpeg, gif, webp,
avif, pdf, plain text). Everything else is stored in `application/octet-stream`,
therefore downloaded instead of rendered — which an attachment link already does.
`isImage` now decides on the SERVI type and not on the announced type, to
that a file transferred to octet-stream does not still go to `![](…)`.

### 3. PR attachment upload without rate limiting — **low**

`app/api/pull-requests/[prId]/attachments/route.ts:37` (before fix)

Sister route `POST /api/issues/[id]/attachments` received a `checkSessionRateLimit`
in this same window (hardening commit MIN-118); this one, written for
MIN-162, never had one.

**Scenario.** The same user as above, once accessing a PR
obtained, loops on uploads of 20 MB (the ceiling of the bucket). Nothing
stops it: unbounded growth of a public bucket, on the billed storage of the
project, without any PR needing to really exist on the forge side.

**Fixed** — `checkSessionRateLimit(auth.userId, "pr-attachment-create")`
(60/min, default), after gatekeeping.
