## Implementation guarantees

Ordinary forge registration and direct updates cannot create a positive proof.
Guarded proof RPCs trust the privileged byte-authenticating application path;
SQL itself cannot authenticate Storage bytes. Independent application readiness
authenticates the bytes again. SQL guards fence old writers, replacement mutation, rotation, and abandonment while
legacy cleanup is pending. Restored registration inserts become unchecked;
direct positive proof updates require the guarded path. Cleanup is idempotent,
batch progression is fair, and CAS conflicts are failures rather than proof.
Missing, clear, truncated, corrupted, wrong-key, historical-key, and concurrently
changed objects are exercised. An authenticated historical envelope is not a
current-key completion proof until safely rotated and verified.

Agent allocations use unique physical generation names and a durable ledger
that survives parent erasure and independently ordered restores. Account/project
locks fence reservation and attachment against erasure in both orders. Failed
attachment revokes the pending request. Key intent is recorded before minting;
new keys must be revoked even if their provider outcome is uncertain. Erasure
success includes an all-row SQL completeness oracle, not just a potentially
truncated REST listing. Unknown allocation/key outcomes deliberately remain
blockers until reconciled; a timeout or a pre-allocation 404 is not success.

Client snapshots keep decryption keys off the browser and Electron renderer.
Cached project responses are bound to current access fingerprints; account-owned
authored drafts are a deliberate bounded recovery copy, not project-erasure
closure. Guest drafts use the live feedback-board capability and a random nonce,
not account authentication. See [local-client-copies.md](local-client-copies.md)
for slot limits, retention, offline limitations, deletion, legacy data, and
historical endpoint-copy scope. Login email remains a narrow Auth exception;
arbitrary account import metadata is not exempted.

## Isolated PostgreSQL verification

The final verification template was rebuilt from an empty isolated database and
the frozen migration files, including all seven migrations added here:
`minddy_min591_final_verified_20260929` in
`supabase_db_minddy-encryption-test`. The template had zero Auth users, project
keys, and allocation rows before and after clone-based verification. Every
fixture was synthetic. No production database or bucket was used.

The refreshed inventory contains **199 tables, 1,785 columns, 173 encrypted
targets, 1,735 TS/JS consumer candidates, 558 functions, 10 views, 491 triggers,
and 214 migration files**. These are inventory counts, not encryption proofs.

Recorded isolated results:

- 98 SQL regression scripts passed on the final schema, including activation
  suspension, old-writer refusal, CAS, access, and authenticated proof guards.
- Three historical marker regressions passed as genuine before/after migration
  replays on disposable historical clones, rather than being skipped at HEAD.
- 76 opt-in Vitest database cases passed serially: 70 recovery cases, two forge
  recovery cases, and four backfill/write-fence cases.
- Eleven snapshot/activation scenarios and four feedback session/OTP concurrency
  orders passed in final-template mode; the historical mode also passed.
- Eight real two-session allocation reservation/attachment versus account/project
  erasure orders passed. Forge tests also exercised four real two-session
  cleanup/rotation races.
- Five PostgreSQL search-oracle tests passed, including the deterministic
  9,200-row rank/order corpus and RLS/limit checks.

Restore coverage uses real PostgreSQL dumps, independently restored parents and
children, multiple key versions, cold managed-key caches, and a wrong wrapping
root. Forge reference/object ordering tests use **simulated Storage bytes** with
real application cryptography and SQL metadata restoration. They do not validate
the real Storage service's backup, consistency, or restoration procedure. That
service-level rehearsal remains a migration gate.

An intermediate test-harness run incorrectly shared a mutable template between
concurrent clone/replay jobs and reapplied historical migrations onto HEAD.
The final runs instead used the immutable empty final template, serial clones,
and explicit final-template fixture mode. No failed harness result is counted
as a passing product proof.

## Remaining gates

1. Inventory and close historical database, Auth metadata, device/profile,
   telemetry/log, export, backup, and pre-ledger provider copies. Inactive device
   expiry enforcement is not proof of physical deletion. Account-owned drafts
   retained after project revocation are not a closed project-erasure target.
2. Rehearse real SQL/Storage service restoration in independent batches and
   orders, validate recoverability with all required historical roots and keys,
   and reconcile every unknown provider/key ledger outcome before migration.
3. Quiesce pre-ledger executors and old writers; preserve tested fail-closed
   flags, complete each target's verified backfill/rotation, and only then
   consider removing clear compatibility data and enabling reads/writes.
4. Measure representative staging search, latency, concurrent load, cold/warm
   key-cache behavior, and provider cleanup. These are **staging preactivation**
   gates, not a demand for production measurements to validate this code PR.

critical-families/forge-object scope is explicit. Ten critical families returning

replacement, not continuing plaintext double writes. Earlier wiki, ticket, and
document checkpoints are historical and superseded where identified.
