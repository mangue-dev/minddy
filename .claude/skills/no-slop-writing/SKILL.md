# No-slop writing

Text a model writes by default fits the widest range of readers and subjects, so it ends up
saying little, saying it loudly, and saying it twice. A human writing for one reader on one
screen makes uneven, specific choices. This skill turns the first kind of text into the second.

It covers every surface a person reads: marketing pages, product UI, transactional messages and
documentation. Surface-specific rules live in [references/surfaces.md](references/surfaces.md).
The full catalog of tells, with before/after fixes, lives in
[references/patterns.md](references/patterns.md). Language-specific tells (French included) live
in [references/languages.md](references/languages.md).

## The five laws

Everything below derives from these. When a rule and a law conflict, the law wins.

1. **Every sentence adds something the reader does not have yet.** If deleting it loses nothing,
   delete it. This kills restated headings, repeated benefits, recaps, and filler intros.
2. **Emphasis is a budget, and most lines get none.** Only the lines that carry the page's main
   message are allowed to sound like a message. Everything else describes plainly.
3. **State facts, not significance.** Replace "powerful", "seamless", "game-changing", "a new era"
   with what the thing does, how many, how fast, or what step disappears. If you do not have the
   fact, do not invent one.
4. **Say each idea once, in one place, with one word for it.** No synonym cycling, no second
   paragraph that rephrases the first, no feature described three times across a page.
5. **Match the moment.** Tone follows what the user is doing and what is at stake: brief on
   routine success, plain and serious on errors and destructive actions, warmer on first use.

## The emphasis budget (the most common failure)

AI copy puts a tagline in every slot: a card subtitle written like a hero headline, a settings
description with dramatic stakes, a tooltip that ends on a punchline. Assign weight by position:

| Slot | Allowed weight |
|------|----------------|
| Page H1 / hero headline | Full. One clear promise or positioning line. |
| Section headings (H2) | Medium. Name the topic or the benefit in plain words. |
| Hero subheadline | Medium. Explain the H1 concretely: who, what, how. |
| Card titles, feature names | Low. A noun phrase. |
| Card body, descriptions, helper text, tooltips, settings, table cells, labels | None. Factual, descriptive, no rhetoric. |
| Buttons and links | None. Verb + object. |

Signals that a low-weight line is over-budget: a contrast ("not X, it's Y"), a fragment for
effect ("Fast. Private. Yours."), a closing punchline, an abstract noun doing human things ("your
workflow, reimagined"), words like "finally", "truly", "effortless", "magic", "the future of",
"built for the way you work", or a line you could print on a mug.

Fix: rewrite it as the plainest true sentence about what it describes. "Your team's
command center, reimagined" on a dashboard card becomes "See open issues and recent activity
across your projects."

## Empty and elongated text

Long text is fine when every part is load-bearing. These are not:

- **Restating the visible.** "Click the button below to continue" above a "Continue" button. A
  heading followed by a sentence that repeats it. Helper text that repeats the label. Delete.
- **Several ideas crammed into one string.** A button that also explains why; a label that is also
  a sentence; a description welded to a justification. One idea per element: split, or move the
  secondary idea to helper text or a tooltip.
- **Fluent paragraphs with no claim.** Grammatical, polished, says nothing checkable. Test: can
  you underline one specific fact? If not, cut or replace with the fact.
- **Re-explaining what the reader knows.** Background rebuilt before the point; the answer in the
  last line. Lead with the decision or the action.
- **Writing about the text instead of the subject.** "This section shows...", "Below you'll find
  ...", "We've designed this page to...". Delete; let the content speak.
- **Stacked qualifiers and hedges.** "could potentially help you to..." becomes "helps you...", or
  a precise limit if one exists.
- **Lists padded to three.** If only two items are real, write two.
- **Notes for the developer.** TODO, placeholder, "coming soon" for nothing, "this will display",
  "temporary", lorem. Remove, or ask what real copy is intended.
- **Leaked internals.** Endpoints, table names, stack names, raw error codes, env names, HTTP
  status. Translate into what the user experiences, or remove.
- **Stale descriptions.** Copy describing steps, options, limits or buttons the code no longer
  has. When copy makes a claim about behavior, check the component that renders it and make the
  text match the code. If the intent is ambiguous, ask.

Rough length budgets (heuristics, not hard limits): buttons 2-4 words (max ~24 chars), nav items
~20 chars, chips and badges ~15 chars, titles 3-6 words, error messages 12-18 words including the
fix, instructions under 20 words, body sentences averaging 15-20 words and rarely above 25.

## Workflow

### 1. Get context first

Before changing anything, establish: the product and audience, the surface, the language and
register (tu/vous, formal/casual), existing terminology, and any voice or style guide in the repo.
Read the component around each string, not the string alone. If the register or audience is
unknown and matters, ask.

### 2. Audit before rewriting

Read the whole surface (page, flow, or set of strings) once. Mark tells by strength, using
[references/patterns.md](references/patterns.md):

- **Act on one sighting:** contrast reveals, dramatic fragments and one-line closers, staged
  run-ups ("Here's the thing", "Let's dive in"), inflated significance, chatbot residue, developer
  notes, leaked internals, over-budget emphasis.
- **Act on clusters only:** single AI-favored words, one em dash, one passive sentence, one triad.
  A lone "robust" is a word; four of them in a section are a tell.

Also look at shape, not just sentences: every section ending on a punchline, every card built on
the same template, three parallel examples everywhere, uniform sentence length.

For a large codebase or when the user wants to review first, produce the audit as a list
(location, current text, problem, proposed text) and stop before editing.

### 3. Set the message hierarchy

For each screen or section decide: the one fact the user needs now, the action available next,
supporting context that changes the decision, and the tone for this moment. Assign the emphasis
budget. Then write.

### 4. Rewrite from the facts

- Go back to the underlying fact (the mechanism, number, step, object, consequence) and write the
  plainest sentence that states it. Swapping a flagged word for a synonym creates a new tell.
- Keep every supported claim. Never add a number, name, customer, quote, metric or capability that
  is not in the source, the code, or the user's input. When a sentence needs a fact you do not
  have, write `[NEED: ...]` or ask.
- Keep product terminology, legal meaning, and domain terms the audience knows.
- Use the same noun and verb for the same concept across the product.
- Vary sentence length on purpose. Two items beat a forced three.
- Prefer is/are/has over "serves as", "features", "boasts", "stands as".
- Active voice with a clear actor, usually "you" or the product.

### 5. Verify

Read the result in context (in the rendered UI when possible) and check:

- [ ] No line below H1/H2 carries tagline-level emphasis.
- [ ] No sentence could be deleted with nothing lost.
- [ ] No idea appears twice on the same surface.
- [ ] No contrast reveal, negation list, fragment run, colon reveal, or self-answered question.
- [ ] No inflated significance or sales adjectives without a fact behind them.
- [ ] No facts added that were not in the source; no supported claim lost.
- [ ] Every button says what happens; every error says what failed and what to do.
- [ ] Terminology and register are consistent; casing follows the project convention.
- [ ] Copy that describes behavior matches what the code does.
- [ ] Strings fit their containers at realistic widths and in longer languages.
- [ ] Re-scan for the tells that survive rewrites: contrasts, closers, triads, dashes, bold labels.

## Guardrails

- **Do not over-correct.** All-short sentences, forced casualness, bolted-on slang, ellipses used
  to dodge a dash, and fake typos are a newer tell, not a fix. The goal is a plain, consistent
  voice, not an anti-AI costume.
- **Some patterns are fine on purpose:** a single "No credit card required" near a CTA, a list of
  three when there are three features, an FAQ written as questions, a short punchy H1, a contrast
  that corrects a belief the reader actually holds.
- **Protected content stays untouched:** code, identifiers, i18n keys, URLs, legal text, quotes,
  testimonials, brand names. Report problems there instead of rewriting.
- **Copy first, display second.** Truncation or tooltips only for text whose full length is
  legitimately needed; if the text itself is too long, rewrite it.
- **i18n:** edit only the value at the target key; list other locales with the same key for
  re-translation instead of translating them yourself. Write complete sentences rather than
  concatenated fragments so translators can reorder.
- **Never invent.** Uncertainty is surfaced as a question, not filled with a plausible guess.
